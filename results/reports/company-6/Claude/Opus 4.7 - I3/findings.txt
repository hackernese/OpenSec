# Finding: Unauthenticated osTicket Installer Exposed - Full Application Takeover
Severity: critical
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H (9.6)
Affected: https://ticket.ausecurity.best/setup/install.php, https://ticket.ausecurity.best/setup/, http://51.79.166.209:8080/setup/install.php
References:
- OWASP A05:2021 - Security Misconfiguration
- osTicket Documentation: Post-Install Hardening (removal of /setup directory)
- CWE-1188: Insecure Default Initialization of Resource

Summary:
The osTicket 1.18.4 installer at https://ticket.ausecurity.best/ is publicly reachable and running in a fresh/uninitialized state. Every application path (/scp/, /tickets.php, /login.php, /api/, etc.) issues a 302 redirect to /setup/install.php, confirming the system has never been configured. An unauthenticated internet attacker can therefore walk through the installer, supply their own database connection and admin credentials, and gain full administrative control of the osTicket platform before the legitimate owner completes setup.

Description:
Direct GET requests to https://ticket.ausecurity.best/setup/install.php return HTTP 200 with the "osTicket Installer" welcome page, including a PHP prerequisite screen (PHP 8.2.33, MySQLi loaded) and a "Continue" button that advances to database and administrator-account configuration. The same installer is also exposed in plaintext via the backend Apache (http://51.79.166.209:8080/setup/install.php) which responds identically regardless of the Host header, bypassing the nginx frontend entirely.

Business impact: an attacker completing the installer would obtain the first admin account and could then weaponise osTicket as a trusted inbound channel (phishing with legitimate ausecurity.best tickets, exfiltration of customer PII once real tickets are opened, deployment of a malicious knowledge-base article as a watering hole, and persistent code execution via plugins or email-piping scripts).

Evidence:
- /home/research/Projects/AuSecurity/evidence/P5-ticket/install-page-head.txt (installer welcome screen)
- /home/research/Projects/AuSecurity/evidence/P5-ticket/path-probe.txt (every /scp/*, /ajax.php, /login.php redirects to /setup/install.php)
- /home/research/Projects/AuSecurity/evidence/P5-ticket/8080-install-headers.txt (installer also reachable on plaintext 8080)
- /home/research/Projects/AuSecurity/evidence/P5-ticket/install-headers.txt

Recommendation:
1. Immediately disable public reachability of /setup/ (nginx `location /setup/ { deny all; }` or filesystem removal `rm -rf /var/www/html/setup/` once installation is finished - per osTicket's official post-install hardening).
2. Complete the installation yourself with strong credentials before an attacker does.
3. Block external access to the Apache backend on 51.79.166.209:8080 at the host firewall / OVH network tab; only the nginx reverse proxy should reach it (loopback / private network).
4. Audit the osTicket database for any records created before you complete setup to detect prior attacker activity.

Severity: high
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:C/C:L/I:H/A:N (7.1)
Affected: ausecurity.best (and all subdomains - no subdomain policy published)
References:
- RFC 7208 (SPF), RFC 6376 (DKIM), RFC 7489 (DMARC)
- M3AAWG Email Authentication Recommendations
- CWE-290: Authentication Bypass by Spoofing

Summary:
The ausecurity.best DNS zone publishes no SPF, DKIM, DMARC, MX, MTA-STS, or TLS-RPT records. Any attacker on the internet can send email that appears to come from any @ausecurity.best address (including info@, owner@, admin@) and recipient mail servers have no cryptographic or policy signal to reject it. In parallel, the published contact address info@ausecurity.best is undeliverable because there is no MX record pointing at a mail server.

Description:
Direct DNS queries confirm complete absence of email-authentication records:
- MX ausecurity.best: no answer
- TXT ausecurity.best (SPF): no v=spf1 record
- TXT _dmarc.ausecurity.best: no answer
- TXT <selector>._domainkey.ausecurity.best (tested: default, google, selector1, selector2, mail, s1, s2, k1, dkim): no answer
- TXT _mta-sts.ausecurity.best / _smtp._tls.ausecurity.best: no answer

Business impact: an attacker can impersonate AuSecurity in Business Email Compromise (BEC) attacks against clients, suppliers, Flinders University contacts, or prospective customers. Because AuSecurity publicly positions itself as a GRC consulting and penetration-testing firm, successful spoofing is particularly damaging to brand trust and could also be used to lure the firm's own clients into disclosing sensitive data. The absence of an MX record also means customers who email info@ausecurity.best (as advertised on the website contact page) receive no reply, which is a direct revenue/reputation issue.

Evidence:
- /home/research/Projects/AuSecurity/evidence/P3-dns/mx.txt
- /home/research/Projects/AuSecurity/evidence/P3-dns/spf.txt
- /home/research/Projects/AuSecurity/evidence/P3-dns/dmarc.txt
- /home/research/Projects/AuSecurity/evidence/P3-dns/dkim.txt
- /home/research/Projects/AuSecurity/evidence/P3-dns/mtasts.txt

Recommendation:
1. Publish a strict SPF record. If no mail is sent from the domain today: `v=spf1 -all`.
2. Publish a strict DMARC policy: `v=DMARC1; p=reject; sp=reject; adkim=s; aspf=s; rua=mailto:dmarc-reports@ausecurity.best; fo=1`.
3. If/when real mail is enabled: set up a provider (Google Workspace / M365 / Fastmail), publish MX records, enable DKIM signing with per-selector 2048-bit keys, and tighten SPF to the provider's include list.
4. Consider MTA-STS (`v=STSv1; id=...; mode=enforce; mx=...; max_age=86400`) and TLS-RPT once mail flow is established.
5. Until mail is set up, replace the published info@ausecurity.best contact with a working channel (e.g., a web form on the marketing site posting into osTicket after it is secured).

# Finding: Backend Apache Server Exposed Directly on Port 8080 (osTicket)
Severity: high
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:L/A:N (8.2)
Affected: http://51.79.166.209:8080/ (ticket.ausecurity.best backend)
References:
- OWASP A05:2021 - Security Misconfiguration
- CWE-668: Exposure of Resource to Wrong Sphere

Summary:
The osTicket backend Apache 2.4.68 instance is directly reachable from the public internet on tcp/8080 without TLS. This bypasses the nginx reverse proxy on 443 and permits identical access to the osTicket installer and application in plaintext. Any security controls that rely on the nginx edge (TLS, future WAF rules, HSTS, request-size limits, rate-limits) can be evaded by connecting to port 8080 directly.

Description:
nmap confirmed 51.79.166.209:8080 open, running Apache/2.4.68 (Debian). The backend responds identically to IP:8080 and to Host: ticket.ausecurity.best, with no virtual-host separation. GET http://51.79.166.209:8080/ returns 302 to /setup/install.php (the installer takeover vector described earlier), and the installer page is fully usable over plaintext HTTP. Positive controls observed on the backend: /server-status returns 403, /server-info returns 404, /.htaccess returns 403, and /include/ost-config.php returns 403.

Business impact: beyond compounding the installer takeover risk by removing TLS, this exposure means credentials entered into the live osTicket admin login (once configured) can be captured by any passive observer on the network path if a client happens to be directed - or redirected - to port 8080.

Evidence:
- /home/research/Projects/AuSecurity/evidence/P1-portscan/209-top1000.nmap
- /home/research/Projects/AuSecurity/evidence/P1-sv/sv-all.nmap
- /home/research/Projects/AuSecurity/evidence/P5-ticket/8080-root.txt
- /home/research/Projects/AuSecurity/evidence/P5-ticket/8080-install-headers.txt
- /home/research/Projects/AuSecurity/evidence/P5-ticket/8080-host-ticket.txt

Recommendation:
1. Block tcp/8080 at the OVH network firewall or on the host `iptables -I INPUT -p tcp --dport 8080 ! -s 127.0.0.1 -j DROP`.
2. Reconfigure Apache to bind to 127.0.0.1:8080 only (`Listen 127.0.0.1:8080` in /etc/apache2/ports.conf) so it is impossible to expose externally.
3. Verify similarly on the apex host (51.79.166.148:8080 also exposes a backend nginx 1.25.5 serving identical content).

# Finding: Session Cookie Set Without HttpOnly, Secure, or SameSite Flags (osTicket)
Severity: medium
CVSS: CVSS:3.1/AV:N/AC:H/PR:N/UI:R/S:U/C:H/I:L/A:N (6.3)
Affected: https://ticket.ausecurity.best/* (PHPSESSID cookie)
References:
- OWASP WSTG-SESS-02, OWASP Secure Cookie Attributes
- CWE-614, CWE-1004, CWE-1275

Summary:
PHPSESSID cookies issued by osTicket (both via nginx:443 and direct Apache:8080) are set with only `path=/`. The HttpOnly, Secure and SameSite attributes are all missing. If a cross-site-scripting flaw is later found (or already exists) anywhere in osTicket, the session cookie can be stolen via JavaScript. The cookie can also be sent in plaintext over port 8080 and leaked in cross-site contexts.

Description:
Observed Set-Cookie header on /setup/install.php response:
`Set-Cookie: PHPSESSID=ecacfde8cdb7c6e1a188972075364a98; path=/`
No HttpOnly, no Secure, no SameSite. nmap -sC also raised the http-cookie-flag ("PHPSESSID flag not set: httponly, secure").

Business impact: once osTicket is in production, a single XSS - a very common class in support-ticket applications where users submit free-form HTML / attachments - would convert into immediate agent-session hijack.

Evidence:
- /home/research/Projects/AuSecurity/evidence/P5-ticket/install-headers.txt
- /home/research/Projects/AuSecurity/evidence/P1-sv/sv-all.nmap

Recommendation:
Configure the PHP session or the web server to add secure cookie attributes:
- PHP (php.ini or FPM pool):
  `session.cookie_httponly = 1`
  `session.cookie_secure = 1`
  `session.cookie_samesite = "Lax"`
- Or set via nginx: `proxy_cookie_flags PHPSESSID httponly secure samesite=lax;`

POST of `<methodCall><methodName>system.listMethods</methodName>...</methodCall>` returned ~80 methods including the three attack-amplifying ones listed above. A pingback.ping test produced a parsed XML-RPC fault response, confirming the method is live.

- /home/research/Projects/AuSecurity/evidence/P4-blog/xmlrpc-pingback.txt

# Finding: WordPress Login and XML-RPC Endpoints Reachable Without Rate Limiting
Severity: low
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:L/A:N (5.4)
Affected: https://blog.ausecurity.best/wp-login.php, https://blog.ausecurity.best/xmlrpc.php
References:
- OWASP WSTG-ATHN-04
- CWE-307: Improper Restriction of Excessive Authentication Attempts

Summary:
Both authentication entry points on the blog respond with HTTP 200 to unauthenticated requests without any evidence of rate-limiting, lockout, CAPTCHA, or source-IP throttling. Combined with the disclosed `admin` username and lack of 2FA, credential attacks against the blog are possible. (We did NOT run a credential attack - the engagement rules forbid credential bruteforce.)

Description:
GET /wp-login.php returns 200 and the standard login form with `wordpress_test_cookie` set. GET /xmlrpc.php returns 200 and the "XML-RPC server accepts POST requests only" message; POST yields full RPC. There is no observable rate-limit header, no fail2ban-style 429 response under repeated hits, and no 2FA indication in the login HTML.

Business impact: credential-spraying from botnets is continuous for every public WordPress login; the probability of eventual success on an `admin` account grows over time without MFA / lockout.

Evidence:
- /home/research/Projects/AuSecurity/evidence/P4-blog/wplogin-headers.txt
- /home/research/Projects/AuSecurity/evidence/P4-blog/xmlrpc-headers.txt

Recommendation:
1. Enforce multi-factor authentication (plugins: Wordfence, miniOrange 2FA, Two Factor).
2. Rename or restrict /wp-login.php (plugin: WPS Hide Login) OR add nginx `allow`/`deny` for the admin management IP range.
3. Enable login lockout + CAPTCHA (Wordfence, Limit Login Attempts Reloaded).
4. Rate-limit the endpoints at nginx: `limit_req_zone $binary_remote_addr zone=login:10m rate=10r/m;` then `location = /wp-login.php { limit_req zone=login burst=3 nodelay; }` and similarly for /xmlrpc.php.

# Finding: WordPress Install and Upgrade Endpoints Reachable (Already-Installed State)
Severity: info
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N (5.3) - lowered to info given no destructive capability on an installed site
Affected: https://blog.ausecurity.best/wp-admin/install.php, /wp-admin/upgrade.php
References:
- CWE-200

Summary:
Unauthenticated requests to /wp-admin/install.php and /wp-admin/upgrade.php return HTTP 200 showing "Already Installed" and "No Update Required" respectively. Unlike the osTicket case these endpoints do not allow re-installation, but their reachability leaks state and provides low-value reconnaissance.

Description:
Body of /wp-admin/install.php contains "Already Installed - You appear to have already installed WordPress. To reinstall please clear your old database tables first." /wp-admin/upgrade.php shows "No Update Required". These confirm the WP installation is complete and current with its DB schema.

Recommendation:
Deny unauthenticated access via nginx:
```
location ~* /wp-admin/(install|upgrade)\.php$ { allow <admin IP>; deny all; }
```
or delete `install.php` after install (WordPress supports this).

- /home/research/Projects/AuSecurity/evidence/P4-blog/upgrade-body.html
