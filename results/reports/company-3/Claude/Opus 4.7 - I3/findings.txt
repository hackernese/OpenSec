# Finding: Publicly Exposed AWS Root Account Credentials in Client-Side JavaScript
Severity: critical
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H (9.8)
Affected: https://imagesharer.xyz/js/awsvalid.js (A1), AWS Account 016170038077
References:
- https://cwe.mitre.org/data/definitions/798.html (CWE-798: Use of Hard-coded Credentials)
- https://cwe.mitre.org/data/definitions/312.html (CWE-312: Cleartext Storage of Sensitive Information)
- https://cwe.mitre.org/data/definitions/540.html (CWE-540: Inclusion of Sensitive Information in Source Code)
- https://docs.aws.amazon.com/IAM/latest/UserGuide/best-practices.html#lock-away-credentials

Summary:
Imagur's public website serves a JavaScript file that contains, in a commented-out block, a live AWS access key and matching secret for the AWS root account that owns the application's cloud environment. Any visitor (including automated scanners that constantly scrape the internet for AWS keys) can read these credentials from the browser and immediately gain full administrative control of the Imagur AWS account.

Description:
The file https://imagesharer.xyz/js/awsvalid.js is a public static JavaScript asset. Lines 3–7 contain:

    /*
    AKIAQHQ6PGM62T2FFPGU
    c7njNpv1oT3rhBhUHue2e2d+oIFnw7QDgCmTtPCG
    ap-southeast-2
    */

A read-only `aws sts get-caller-identity` call using the exposed credential returned:
    UserId:  "016170038077"
    Account: "016170038077"
    Arn:     "arn:aws:iam::016170038077:root"

Because the ARN ends in `:root`, this is NOT a scoped IAM user; it is the AWS account root user. Root credentials bypass all IAM policies and permission boundaries and can:
- Read, modify, or delete every resource in the account (S3 data, databases, EC2, IAM users, billing, DNS/Route53, CloudFront, backups, etc.).
- Create new IAM users and backdoors.
- Close the AWS account.
- Incur unbounded costs (crypto mining, data egress).
- Change billing/payment information and tax identity.

Business impact:
- Complete loss of confidentiality, integrity, and availability of all data and services hosted in AWS account 016170038077.
- Likely data breach affecting any user data stored by Imagur.
- Possible full account takeover / destruction / financial loss.
- Public bots scrape GitHub, Pastebin, and the open web continuously for AKIA-prefixed strings; exposure time, not just presence, drives risk. If the key has been online for any meaningful period it should be treated as already compromised.

Evidence:
- /home/research/Projects/Imagur/evidence/p0-awskey/awsvalid.js (full captured file)
- /home/research/Projects/Imagur/evidence/p0-awskey/awsvalid.headers.txt (HTTP 200, text/javascript)
- /home/research/Projects/Imagur/evidence/p0-awskey/sts-get-caller-identity.json (ownership verified)

Recommendation:
IMMEDIATE (within hours):
1. Log into the AWS Console as root and rotate the root access key: deactivate then delete AKIAQHQ6PGM62T2FFPGU immediately. (IAM → Security credentials → Access keys.)
2. Enable Multi-Factor Authentication (MFA) on the root user if not already enabled.
3. Review CloudTrail event history for AWS Account 016170038077 for the last 90 days. Look for any API calls originating from unfamiliar IPs or using the leaked access key ID. Pay special attention to IAM, S3, EC2, and RDS activity.
4. Remove the credential block entirely from awsvalid.js and redeploy. Confirm it is no longer served (hard-refresh test).
5. Rotate every other secret that may have been stored in the same account (S3 bucket keys, DB passwords, API tokens) because an attacker with root could have exfiltrated them.

SHORT TERM (within days):
6. Follow AWS root-account best practice: do not use the root user for day-to-day operations. Create a dedicated IAM user (or IAM Identity Center user) with only the permissions the application actually needs, and use that from here on.
7. Implement AWS GuardDuty + billing anomaly alerts to detect reuse of leaked credentials or sudden spend changes.
8. Add a secret-scanning gate to the deployment pipeline (e.g., gitleaks, trufflehog) so no commit containing AKIA/ASIA/AWS secret patterns can be released.
9. Any client-side code that needs to talk to AWS must use short-lived temporary credentials (Amazon Cognito, STS AssumeRoleWithWebIdentity) — never a long-lived root key.

LONG TERM:
10. Adopt a secret manager (AWS Secrets Manager / HashiCorp Vault) for all backend secrets; never ship secrets in client-side JavaScript regardless of comment status, because every byte sent to the browser is public.

# Finding: PostgreSQL Database Server Exposed to the Public Internet
Severity: high
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:L (6.5)
Affected: 51.161.131.44:5432/tcp (A4), the application database backing https://imagesharer.xyz/
References:
- https://cwe.mitre.org/data/definitions/668.html (CWE-668: Exposure of Resource to Wrong Sphere)
- https://www.postgresql.org/docs/current/auth-pg-hba-conf.html
- https://cheatsheetseries.owasp.org/cheatsheets/Network_Segmentation_Cheat_Sheet.html

Summary:
The database that powers imagesharer.xyz is reachable from any address on the public internet. The application and the database are hosted on the same server, so there is no legitimate reason for anyone outside the server itself to connect to port 5432. Leaving the port open creates a direct path for attackers to attempt credential guessing, exploit any PostgreSQL vulnerability, and (if they obtain credentials) steal, modify, or destroy all image and user data.

Description:
A targeted service probe to 51.161.131.44 TCP/5432 returned:
    PORT     STATE SERVICE    VERSION
    5432/tcp open  postgresql PostgreSQL DB
    Protocol: 3.0 (confirmed via PostgreSQL error response)
    TLS on 5432: not configured

The service accepts arbitrary TCP connections from the internet. No authentication attempt was made (that is out of scope for the engagement rules of engagement), but the exposure alone materially increases risk:
- Any attacker, including unattended internet-wide scanners, can connect and attempt to authenticate.
- Credential guessing against pg_hba.conf's md5/scram-sha-256 is possible at scale.
- Historical PostgreSQL CVEs (RCE, authentication bypass, privilege escalation) are reachable before they can be patched.
- Data is transmitted in cleartext because TLS is not enforced on the port.

Business impact:
- A single stolen or guessed database password equals full loss of user data (images, usernames, password hashes, email addresses, sessions).
- Compliance implications under the Australian Privacy Act / Notifiable Data Breaches scheme if real user data is accessed.

Evidence:
- /home/research/Projects/Imagur/evidence/p0-postgres/nmap-5432.txt

Recommendation:
IMMEDIATE:
1. Restrict TCP/5432 at the firewall. The simplest fix on OVH is one of:
   - Edit postgresql.conf: `listen_addresses = 'localhost'` and restart PostgreSQL. The web app on the same server will still connect via 127.0.0.1.
   - If a separate DB host is needed, allow 5432 only from the application's IP in `pg_hba.conf` AND restrict with ufw/iptables / OVH security group.
2. Verify no PostgreSQL password uses "postgres", "password", "admin", or an empty value. Rotate the application's DB user password to a long, randomly generated secret.
SHORT TERM:
3. Enable TLS on PostgreSQL (`ssl = on`) with a valid certificate, and require `hostssl` entries in pg_hba.conf.
4. Enable pg_hba.conf method `scram-sha-256` (not md5) for all users.
5. Keep PostgreSQL packages patched (currently ambiguous on-wire version — ensure latest 16.x LTS).
6. Add fail2ban or equivalent to lock out hosts after repeated failed PostgreSQL logins.

# Finding: Dangling / Misconfigured CloudFront Alias on resources.imagesharer.xyz

- https://cwe.mitre.org/data/definitions/1104.html (CWE-1104: Use of Unmaintained Third Party Components)
- https://cwe.mitre.org/data/definitions/295.html (CWE-295: Improper Certificate Validation)

Summary:
Imagur's DNS points `resources.imagesharer.xyz` to an AWS CloudFront distribution that is not configured to accept that hostname. Browsers requesting the URL see a security warning (the TLS certificate does not cover the hostname), and the distribution returns HTTP 403 for every request. The intended behavior (serving the site's favicon from `https://resources.imagesharer.xyz/icon.ico`) is broken. In addition, the state leaves open a smaller risk of future takeover if the CloudFront distribution is ever deleted while the DNS record remains.

- TLS (SNI resources.imagesharer.xyz): certificate CN=*.cloudfront.net, SANs = *.cloudfront.net, cloudfront.net only — DOES NOT include resources.imagesharer.xyz, so every browser request raises a certificate error.
- HTTP: 403 Forbidden on both `/` and `/icon.ico` with headers `Server: CloudFront` and `X-Cache: Error from cloudfront`, confirming the distribution exists but does not have `resources.imagesharer.xyz` listed as an alternate domain name (AKA CNAME alias).
- Direct access to `d273uevi0662l0.cloudfront.net` reveals an origin of AmazonS3 (empty 404), meaning the origin bucket is either empty or unconfigured.
- The main login page references this hostname (favicon), so users who view page source or any future dependency on this host will encounter broken resources and TLS warnings — degrading trust and triggering browser phishing-detection heuristics on some clients.

Takeover risk: If the CloudFront distribution is ever deleted (common during cost cleanup) and the DNS CNAME is not removed, a different AWS customer who creates a new distribution could coincidentally be assigned a different edge, but with CloudFront alias configuration they could attempt to serve content for resources.imagesharer.xyz. The present risk is low (the distribution is active), but it will materialize the moment the distribution is deleted.

Business impact:
- Broken intended functionality (favicon / static assets).
- Loss of user trust if any URL is shared publicly (browser certificate warning page).
- Latent subdomain-takeover risk if the distribution is ever deprovisioned.

Evidence:
- /home/research/Projects/Imagur/evidence/p0-cloudfront/cloudfront-check.txt

Recommendation:
Choose ONE:
A) If the CDN subdomain is still needed:
   1. In the CloudFront distribution (d273uevi0662l0.cloudfront.net) → Settings → Alternate domain names (CNAMEs), add `resources.imagesharer.xyz`.
   2. Request a public ACM certificate (us-east-1 region) for `resources.imagesharer.xyz` and attach it to the distribution.
   3. Confirm the S3 origin bucket contains the expected content (icon.ico, static assets) and that the Origin Access Control is correctly configured.
B) If the CDN subdomain is NOT needed:
   1. Delete the `resources.imagesharer.xyz` CNAME record at the DNS provider (Spaceship).
   2. Remove the (commented) HTML reference in the login page.
C) General:
   3. Document a rule in deployment/off-boarding checklists: never delete a CloudFront distribution or S3 bucket without first removing or re-pointing the DNS record that points to it.

# Finding: Mass Assignment / IDOR on Image Upload (Attacker Uploads Images to Any Victim Account)
Severity: high
CVSS: CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:L/I:H/A:L (7.6)
Affected: POST https://imagesharer.xyz/images/upload
References:
- https://cwe.mitre.org/data/definitions/639.html (CWE-639: Authorization Bypass Through User-Controlled Key)
- https://cwe.mitre.org/data/definitions/915.html (CWE-915: Improperly Controlled Modification of Dynamically-Determined Object Attributes / Mass Assignment)
- https://owasp.org/API-Security/editions/2023/en/0xa3-broken-object-property-level-authorization/

Summary:
When a signed-in Imager user uploads a picture, the upload form includes a hidden "user_id" field that identifies who owns the image. The server trusts whatever value the browser sends in that field instead of looking up who is actually logged in. Any logged-in user can therefore paste another member's user ID into the request and the picture is saved as if that other member uploaded it — appearing on their dashboard, counted against their quota, and attributed to them in any audit log.

Description:
Upload page HTML (/images/upload) includes:
    <input name="user_id" type="hidden" value="<caller's own UUID>">
    <input name="file" type="file" required>
    <input name="is_public" type="radio" ...>

Reproduction (verified in the engagement):
1. Account A (UUID c9178440-59d6-4715-b8dc-782c592c5885) was authenticated via PHPSESSID.
2. Multipart POST to /images/upload with field user_id = Account B's UUID (0c3f8747-73f2-4f1f-b453-010f5b7fa950).
3. Server returned HTTP 302 Location: /images/ed9b9ab1-b69c-40a7-a2eb-3582f889a67c.
4. Account B's dashboard (fetched independently) now shows image ed9b9ab1-b69c-40a7-a2eb-3582f889a67c as owned by B, even though B never uploaded it.

Full raw request/response captured in /home/research/Projects/Imagur/evidence/p2-uploads/idor/.

Business impact:
- An attacker can plant content on any victim's account. For an image-sharing platform this is severe: an attacker can plant unlawful or defamatory images under a known user's name, exposing that user (and Imagur) to legal, reputational, and law-enforcement consequences. In the worst case, Imagur itself may be served with takedown notices for content it believes a specific user chose to upload.
- Can be used to exhaust a user's storage quota (DoS at the user level) or spam a victim's gallery.
- Attribution/forensic trail is destroyed: logs will say "User B uploaded X" when in fact User A did.

Evidence:
- /home/research/Projects/Imagur/evidence/p2-uploads/idor/baseline.body, baseline.headers
- /home/research/Projects/Imagur/evidence/p2-uploads/idor/idor.body, idor.headers
- /home/research/Projects/Imagur/evidence/p2-uploads/idor/dash-a.html, dash-b.html

Recommendation:
1. Remove the hidden user_id field from the HTML form entirely — the browser cannot be trusted to tell the server which user is logged in.
2. In the upload handler, derive the owning user_id SOLELY from the authenticated session (e.g., $_SESSION['user_id']). Discard any user_id value that arrives in the POST body.
3. Add an integration test: as user A, submit a crafted multipart POST with user_id = user B. Assert the stored row's owner matches A.
4. Review every other endpoint that takes an entity ID in the body for the same pattern (POST /profile/avatar, POST /logout, POST /images/{id}/visibility — see separate finding).
5. Consider migrating to a framework-level pattern (e.g., Laravel's $request->user() / policies) that makes it hard to accidentally trust client-supplied owner IDs.

# Finding: Broken Access Control on Image Visibility Toggle (IDOR — Attacker Makes a Victim's Private Image Public)
Severity: high
CVSS: CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:L/A:N (7.1)
Affected: POST https://imagesharer.xyz/images/<uuid>/visibility
References:
- https://cwe.mitre.org/data/definitions/639.html (CWE-639)
- https://cwe.mitre.org/data/definitions/285.html (CWE-285: Improper Authorization)
- https://owasp.org/Top10/A01_2021-Broken_Access_Control/

Summary:
Any logged-in user who knows (or guesses from an email, dashboard link, or shared URL) another user's image ID can switch that image from "private" to "public" without owning it. Private images therefore are not reliably private: a single HTTP request from another member exposes them to the open internet.

Description:
Reproduction (verified):
1. Account B uploaded a PRIVATE image (ID 925e5bda-6b04-4dfb-9b92-d557da791d57).
2. Account A sent `POST /images/925e5bda-6b04-4dfb-9b92-d557da791d57/visibility` with body `is_public=true`, authenticated as A.
3. Server responded 302 to the image detail page (success flow).
4. Account B's dashboard subsequently displayed the image as 🌍 Public without B taking any action.

The server does not check that the authenticated user owns the image before changing a sensitive property. The same pattern on the delete endpoint was observed to be correctly gated (image remained after A's attempt), confirming that an authorization check exists in the code base — it simply was not applied here.

Business impact:
- Direct violation of the user's privacy expectation ("Private = only you").
- A malicious or compromised account can run through every image UUID it learns about (shared links, scraping public pages, leaked log data) and silently flip them to public. The now-public image is retrievable via its /images/<uuid> page AND via a long-lived S3 pre-signed URL (see separate finding).
- Combined with the image upload IDOR above, an attacker can plant an image on a victim's account AND make it public, then advertise the URL — a credible content-planting + exposure attack.

Evidence:
- /home/research/Projects/Imagur/evidence/p2-authz/authz-tests.log
- /home/research/Projects/Imagur/evidence/p2-authz/s3.headers, s3.body

Recommendation:
1. In the visibility handler, SELECT the image row and verify `image.owner_id == $_SESSION['user_id']` BEFORE applying the update. Return HTTP 403/404 otherwise.
2. Apply the same explicit ownership check to every /images/<uuid>/* endpoint. Treat the per-image delete endpoint as the reference implementation and extend the same pattern.
3. Add server-side logging + alerting when an ownership check fails. Repeated failures from one session are a strong IDOR-probing signal.
4. Add a regression test: user A tries to change visibility of a UUID owned by B — expect 403/404 and no DB mutation.

# Finding: Private Images Expose Long-Lived Pre-signed URLs That Bypass "Private" Status
Severity: high
CVSS: CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N (6.5)
Affected: GET https://imagesharer.xyz/images/<uuid> (owner view for PRIVATE images)
References:
- https://cwe.mitre.org/data/definitions/359.html (CWE-359)
- https://cwe.mitre.org/data/definitions/613.html (CWE-613: Insufficient Session Expiration)
- https://docs.aws.amazon.com/AmazonS3/latest/userguide/ShareObjectPreSignedURL.html

Summary:
When the owner of a PRIVATE image opens its detail page, Imager inserts an AWS S3 pre-signed URL into the HTML — including a "Direct link" field that users may copy. This URL is a bearer token that works for anyone, from anywhere, for 7 full days, regardless of whether the image is still marked private. If a user shares the URL once (e.g., messaging, screenshot, log file, help ticket, browser history export), the "private" image is effectively public for a week.

Description:
Reproduction (verified):
1. Account A uploaded a PRIVATE image. ID: 4cbfdbb9-52f1-42e4-ba95-33b32e40ec2b.
2. Account A opened /images/4cbfdbb9-52f1-42e4-ba95-33b32e40ec2b. The HTML included:
   - An `<img src="...X-Amz-Signature=...X-Amz-Expires=604800...">` element.
   - A "Direct link" `<input type="text" readonly>` containing the same signed URL for easy copying.
3. The signed URL was taken out-of-band and fetched with no session cookie, no referrer, from an unrelated client → HTTP 200, image/jpeg, full image bytes.
4. The `X-Amz-Expires=604800` parameter indicates the URL is valid for 7 days regardless of subsequent visibility changes on the Imager side.

(Note: this finding is independent of the bucket-public finding. Even if the bucket is correctly locked down, these pre-signed URLs remain valid, by design of AWS pre-signed URLs, until expiry.)

Business impact:
- Users have a strong, implicit expectation that "Private" means "nobody else can view this". That contract is broken.
- A single accidental URL share leaks the image for 7 days. The URL cannot be revoked individually.
- Combined with the public bucket, the attack surface is huge; even fixing one does not fix the other.

Evidence:
- /home/research/Projects/Imagur/evidence/p2-final/p1-up.*, p1-detail.html, p1-fetch.*

Recommendation:
1. Do NOT render pre-signed URLs for private images on the owner's detail page. Instead, serve a server-mediated endpoint such as GET `/images/<uuid>/raw`, which checks session + ownership + current visibility on every request and streams the file.
2. If pre-signed URLs are kept for public images, cap `X-Amz-Expires` to the minimum operationally required (default 300 seconds). Never 7 days.
3. If a user toggles a public image to private, immediately rotate/overwrite the object (or set a new object key) so any outstanding pre-signed URL stops working.
4. Add a user-visible "Rotate link" button so owners can invalidate the current direct link on demand.

# Finding: Weak Password Policy — Single-Character Passwords Accepted
Severity: medium
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:L/A:N (6.5)
Affected: POST https://imagesharer.xyz/register
References:
- https://cwe.mitre.org/data/definitions/521.html (CWE-521: Weak Password Requirements)
- https://pages.nist.gov/800-63-3/sp800-63b.html (NIST SP 800-63B §5.1.1)

Summary:
The registration form claims to require passwords of 8 characters or more, but this check is enforced only in the browser (HTML `minlength=8` attribute). A direct HTTP POST with a one-character password (`password=a&confirm=a`) is accepted and the account is created with that one-character password. Users following the UI get a reasonable policy; attackers who send raw requests get none.

Description:
Observed:
- Legitimate flow via browser: minlength=8 enforced client-side; UX gated.
- Direct POST: `curl -X POST -d 'email=weakpw-test@test.local&password=a&confirm=a' https://imagesharer.xyz/register` → HTTP 302 (success response).
Also tested the companion issue: mismatched `password` and `confirm` fields are NOT enforced server-side either; the password is set to whatever `password` contains and `confirm` is cosmetic.

Business impact:
- Any user who registers via API, test harness, mobile client, or scripted sign-up can establish an account whose password is trivial to guess.
- When combined with the lack of rate limiting on /login (separate finding) and the user-enumeration on /register (separate finding), credential stuffing / targeted password-guessing becomes very cheap.

Evidence:
- /home/research/Projects/Imagur/evidence/p2-misc/p4.body, p4.headers (1-char password accepted)
- /home/research/Projects/Imagur/evidence/p2-misc/p5.body, p5.headers (confirm mismatch accepted)

Recommendation:
1. Enforce the password policy server-side (minimum 8 characters, mix of character classes OR a length ≥ 12 — follow NIST 800-63B).
2. Server-side validate `password === confirm` and reject with 400 otherwise.
3. Check new passwords against a well-known breached-password list (e.g., HaveIBeenPwned k-anonymity API).
4. Return explicit, actionable validation errors so legitimate users can self-correct.

Affected: POST https://imagesharer.xyz/login
References:
- https://cwe.mitre.org/data/definitions/307.html (CWE-307: Improper Restriction of Excessive Authentication Attempts)
- https://owasp.org/www-community/attacks/Brute_force_attack

Summary:
Failed login attempts are not rate-limited. Five consecutive wrong-password attempts in rapid succession all returned the same `302 → /login` response with no 429, no CAPTCHA, no account lockout, no exponential backoff. An attacker can therefore attempt thousands of passwords per second against a known email without obstruction.

Description:
Five rapid POSTs to /login with the real test email and five different wrong passwords all returned HTTP 302 immediately (sub-200 ms each). No throttling observed.

Business impact:
- Online password guessing against known-good emails (which the registration-enumeration finding makes easy to collect) is feasible.
- Combined with weak-password-policy (users may have 1-char passwords), compromise is realistic.
- Credential stuffing with leaked-password datasets costs essentially nothing to run.

Evidence:
- /home/research/Projects/Imagur/evidence/p2-final/final-tests.log (R-1 section)

Recommendation:
1. Rate-limit /login by (IP + email) key: e.g., after 5 failures in 15 minutes, respond with 429 and a `Retry-After` header for 15 minutes.
2. Add exponential backoff / login-captcha after the second failure within a short window.
3. Alert on sustained high failure rates per IP range for operational awareness.
4. Prefer a WebAuthn / passkey option so password brute force is simply not applicable.

# Finding: User-Enumeration via Registration Endpoint
Severity: low
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N (5.3)
Affected: POST https://imagesharer.xyz/register
References:
- https://cwe.mitre.org/data/definitions/204.html (CWE-204: Observable Response Discrepancy)
- https://owasp.org/www-community/vulnerabilities/Information_exposure_through_differential_error_messages

Summary:
When a visitor attempts to register an email that is already in use, Imager replies with the explicit message "An account with that email already exists.". Attackers can therefore test any email address against the site and learn whether that person has an Imager account. (For comparison, the /login endpoint correctly returns the same message for both unknown-email and wrong-password cases — this is good; /register must be aligned with that behaviour.)

Description:
Verified with explicit POST + follow-up GET of /register as the same session. Known-registered email yields "An account with that email already exists." Unknown emails produce the normal signup success flow (minus the actual account because test uses already-existing creds). Login endpoint returns an identical "Invalid email or password." for both wrong-password and unknown-email (good — do not change this).

Business impact:
- Enables attackers to confirm whether specific individuals have accounts, which supports targeted phishing, social engineering, and credential stuffing campaigns.
- Enables bulk account mapping from a list of email addresses.

Evidence:
- /home/research/Projects/Imagur/evidence/p2-s3-and-enum/retry/getC.html (quoted error)
- /home/research/Projects/Imagur/evidence/p2-s3-and-enum/retry/getA.html, getB.html (login — identical)

Recommendation:
1. On /register, do NOT reveal whether the email is already registered. Return a generic success message and send an email to the address: either (a) a verification email if new, or (b) a "someone tried to re-register this address" notice if already present. The user flow is unchanged for legitimate owners; attackers get no signal.
2. Combine with CAPTCHA + registration rate limiting (per IP, per email) to raise the cost of bulk enumeration.

# Finding: Unhandled Server Error on Empty user_id Parameter (Denial via Malformed Input)

Summary:
When an authenticated user submits an image upload with an empty `user_id` field, the server returns an HTTP 500 "INTERNAL_ERROR" instead of a validated 400 Bad Request. This indicates a missing input-validation path and leaks information about internal state.

# Finding: Missing HTTP Security Headers (HSTS, CSP) and Email Anti-Spoofing (SPF, DMARC)
Severity: low
CVSS: CVSS:3.1/AV:N/AC:H/PR:N/UI:R/S:U/C:L/I:L/A:N (4.2)
Affected: all HTTP responses on https://imagesharer.xyz/; the `imagesharer.xyz` DNS zone
References:
- https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html
- https://datatracker.ietf.org/doc/html/rfc6797 (HSTS)
- https://content-security-policy.com/
- https://datatracker.ietf.org/doc/html/rfc7489 (DMARC)

Summary:
Several low-cost hardening headers and DNS records are missing. Each on its own is minor, but together they weaken defense-in-depth against downgrade attacks, cross-site scripting, and email spoofing.

Description:
Observed on https://imagesharer.xyz/:
- `Strict-Transport-Security`: NOT SET → browsers can be downgraded to HTTP on a hostile network before the first HTTPS visit of a session.
- `Content-Security-Policy`: NOT SET → no second-layer defense against XSS; inline scripts, inline event handlers, and arbitrary CDN origins are permitted.
- `Permissions-Policy`: NOT SET → no restrictions on camera/microphone/geolocation APIs if ever abused by a stored XSS.
- `Cross-Origin-Opener-Policy` / `Cross-Origin-Embedder-Policy`: NOT SET.

Observed in DNS for `imagesharer.xyz`:
- `MX` records: NONE present.
- `SPF` (TXT v=spf1): NOT present.
- `DMARC` (TXT _dmarc.imagesharer.xyz): NOT present.
- `CAA`: NOT present.
→ The domain can be freely spoofed as a sender in email, since there is no SPF `-all`/`v=spf1 -all` policy and no DMARC `reject` policy. Attackers can send mail "from" help@imagesharer.xyz with high deliverability.

Business impact:
- Easier for attackers to run convincing phishing/password-reset lures that appear to come from Imager.
- No protection against TLS downgrade for first-time visitors on hostile networks (cafe wifi, hotels, airport).
- No browser-level containment should a stored XSS appear anywhere in the application.

Evidence:
- /home/research/Projects/Imagur/evidence/p1-discovery/root.headers.txt
- Enumeration YAML (dns_infrastructure / mail_infrastructure sections)

Recommendation:
1. Add response headers at the nginx layer:
   - `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`
   - `Content-Security-Policy: default-src 'self'; img-src 'self' https://filesharer-research.s3.ap-southeast-2.amazonaws.com data:; style-src 'self' 'unsafe-inline'; script-src 'self'; frame-ancestors 'none'; form-action 'self'; base-uri 'self'`
   - `Permissions-Policy: camera=(), microphone=(), geolocation=()`
2. Add DNS records to Spaceship DNS:
   - `imagesharer.xyz. TXT "v=spf1 -all"` (or `-all` plus the real sending host if mail will be sent).
   - `_dmarc.imagesharer.xyz. TXT "v=DMARC1; p=reject; rua=mailto:security@imagesharer.xyz"`.
   - `imagesharer.xyz. CAA 0 issue "letsencrypt.org"` to pin which CAs may issue certificates.
3. After HSTS has been live for ≥ 6 months with no issues, submit the domain to the HSTS preload list.

# Finding: Production Application Also Exposed Over Plaintext HTTP on Port 8080
Severity: medium
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:U/C:H/I:L/A:N (7.1)
Affected: http://51.161.131.44:8080/ (same code base as https://imagesharer.xyz/)
References:
- https://cwe.mitre.org/data/definitions/319.html (CWE-319: Cleartext Transmission of Sensitive Information)
- https://datatracker.ietf.org/doc/html/rfc7258 (Pervasive Monitoring Is an Attack)

Summary:
The Imager application is served not only over HTTPS on port 443 (via the public hostname imagesharer.xyz) but also over PLAINTEXT HTTP on port 8080 directly on the server's IP address. Anyone who visits http://51.161.131.44:8080/ gets the real, logged-in, interactive production application — with no TLS. If a user signs in that way (or is tricked into clicking such a link), their email, password, session cookie, and uploaded images traverse the network in the clear and can be captured by anyone on the same network path.

Description:
- `curl http://51.161.131.44:8080/login` returns the identical "Log in — Imager" HTML as the HTTPS site (byte-identical body).
- The same `/js/awsvalid.js` (containing the leaked AWS root credential) is served from this port.
- The server does NOT redirect port 8080 to HTTPS and does NOT reject plaintext requests.
- There is no vhost gating (Host header does not affect behavior).
- Nothing on the production site advertises port 8080, so this is unlikely to be used by legitimate users — but it is reachable by any scanner on the internet and by any attacker who crafts a link.

Business impact:
- Session hijacking, credential theft, and image theft for any user who authenticates over port 8080.
- Phishing lure: an attacker who sends `http://51.161.131.44:8080/login?return=...` can intercept credentials in a controlled MITM/relay setup.
- Weakens the security story: Imager appears HTTPS-only to the end user, but the backend is reachable in cleartext.

Evidence:
- /home/research/Projects/Imagur/evidence/p3-infra/other-ports/* and port8080/* (banner, title, awsvalid.js, side-by-side hashing)

Recommendation:
1. Close port 8080 at the OS or OVH firewall. If the port is only needed for internal process-manager health checks, bind the Apache listener to 127.0.0.1 instead of 0.0.0.0.
2. If port 8080 must remain publicly reachable (e.g., for a load balancer that cannot be reconfigured right now), make it ONLY serve a permanent HTTPS redirect to https://imagesharer.xyz/, and set `Strict-Transport-Security` on the HTTPS response (see Headers finding) so browsers remember HTTPS.
3. Audit the server for any other Apache/nginx vhost listening on non-443 ports; apply the same policy.

# Finding: Open DNS Resolver on Port 53 (Potential DDoS Amplification Reflector)
Severity: medium
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:N/I:N/A:L (5.8)
Affected: 51.161.131.44:53 (udp/tcp)
References:
- https://www.cisa.gov/news-events/alerts/2013/03/29/dns-amplification-attacks
- https://www.cloudflare.com/learning/dns/dns-amplification-attack/
- https://openresolverproject.org/

Summary:
The server is running an open DNS resolver that recursively answers queries from anyone on the internet. The server returned a correct answer when asked to resolve `example.com` from an unrelated source address. Open resolvers are routinely abused as reflectors in DDoS amplification attacks, where an attacker spoofs a victim's IP, sends a small query, and the resolver sends a large reply to the victim. Imager's server would be the unwitting attacker in such an attack — leading to IP reputation damage, upstream provider complaints, and potential service degradation while the DDoS traffic is sourced from this host.

Description:
- `dig @51.161.131.44 example.com +short` returned Cloudflare IPs for example.com, confirming full recursive resolution for an off-domain query.
- `version.bind CHAOS TXT` and `hostname.bind CHAOS TXT` were blocked / returned no useful banner — good.
- Direct impact to Imagur is modest, but reputational and operational exposure is real: upstream (OVH) may null-route the host under abuse complaint; the server contributes to internet-wide DDoS.

Business impact:
- Potential upstream null-route by OVH if the server is reported in a DDoS incident.
- Resource consumption during amplification abuse (bandwidth, CPU).
- Reputational: Imagur's IP may land on abuse databases, affecting outbound mail or API callbacks later.

Evidence:
- /home/research/Projects/Imagur/evidence/p3-infra/other-ports/probe-other.log

Recommendation:
1. If this server is not supposed to be a DNS server, STOP the resolver daemon (bind9/unbound/dnsmasq/systemd-resolved) or bind it to 127.0.0.1 only.
2. If it must run DNS, restrict recursion with ACLs:
   - BIND:    `allow-recursion { 127.0.0.1; <trusted-ranges>; };`
   - Unbound: `access-control: 0.0.0.0/0 refuse` then allow specific ranges.
3. Add rate limiting (`rate-limit { responses-per-second 5; };` in BIND) as defense-in-depth.
4. Verify the fix publicly via https://openresolverproject.org/ or `dig @51.161.131.44 example.com` from an off-net client.

# Finding: SSH (OpenSSH 10.0p2) Exposed to the Public Internet
Severity: info
CVSS: n/a
Affected: 51.161.131.44:22/tcp
References:
- https://cheatsheetseries.owasp.org/cheatsheets/SSH_Hardening_Cheat_Sheet.html

Summary:
SSH is open to the entire internet. This is extremely common for small cloud VPSes but still represents an unnecessary attack surface. There is nothing immediately exploitable in the OpenSSH banner (10.0p2 is current), but any future SSH CVE or any weak password / credential leak becomes directly exploitable from anywhere.

Description:
Nmap banner: `22/tcp open ssh OpenSSH 10.0p2 Debian 7+deb13u4 (protocol 2.0)`. No evidence of banner suppression; no attempt was made (nor permitted) to authenticate.

Recommendation (defense in depth, not urgent):
1. Restrict SSH to the administrator's IP / VPN at the OVH firewall or via `AllowUsers`/`Match Address` in sshd_config.
2. Disable password authentication (`PasswordAuthentication no`) and allow only public-key auth.
3. Disable root login (`PermitRootLogin no` or `prohibit-password`).
4. Install `fail2ban` and set `MaxAuthTries 3` to deter online guessing.
5. Keep OpenSSH patched promptly (automated apt-upgrade or unattended-upgrades).
