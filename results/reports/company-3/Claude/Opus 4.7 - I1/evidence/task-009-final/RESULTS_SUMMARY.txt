TEST 3: Port 8080 Exposure (Cleartext HTTP)
--------
Objective: Assess if port 8080 shares same database and has session/credential risks
Result: ✗ MULTIPLE ISSUES FOUND

3a. Login page accessible on cleartext HTTP
  - Port 8080 hosts Apache 2.4.68 (different from HTTPS nginx)
  - /login endpoint responds with HTTP 200
  - Same application code running (HTML form structure identical)
  - Server: "Apache/2.4.68 (Debian)" vs nginx on 443

3b. Database backend shared
  - Successfully registered new account: clawsec.test.final@example.com
  - Registration completed with HTTP 302 redirect to /dashboard
  - **CRITICAL**: PHPSESSID cookie set WITHOUT Secure flag
    Set-Cookie: PHPSESSID=f7982d5acaaf5cda7a665475466d4a46; path=/
    (lacks: Secure, HttpOnly flags)

3c. Cleartext session transmission
  - User A login attempt on port 8080 succeeded (HTTP 302)
  - Multiple PHPSESSID values returned:
    Set-Cookie: PHPSESSID=0475dc7b63a947b67eb12bcc1da7669b; path=/
    Set-Cookie: PHPSESSID=9581b063931e71463504716185dc2e0a; path=/
  - Neither includes Secure flag (will be sent over cleartext HTTP)
  - last_login cookie uses Secure flag but PHPSESSID does not
  - Session keys transmitted in plaintext over HTTP 8080

Findings:
  1. Port 8080 operates same application without HTTPS
  2. Session cookies vulnerable to interception on cleartext channel
  3. Attackers on network path can capture valid session IDs
  4. Same database allows cross-protocol account compromise

TEST 4: PostgreSQL Port 5432 (Fingerprinting only)

4a. TCP connection possible

  - Timeout on raw TCP handshake (no pre-authentication banner)

4b. PostgreSQL authentication prompt received
  - psql connection attempt triggered "Password for user postgres:" prompt
  - Indicates PostgreSQL is running and accepting connections
  - Version not leaked in connection error (good)
  - Error message: "fe_sendauth: no password supplied"

4c. SSL/TLS capability check (STARTTLS)
  - PostgreSQL attempted TLS 1.3 negotiation
  - Handshake started but failed (expected without valid certs)
  - Confirms server supports encrypted connections
  - No version information leaked

Findings:
  1. PostgreSQL port exposed on internet-facing IP
  2. Database accessible for brute-force password attacks (if no rate limiting)
  3. TLS support available but not enforced at connection level
  4. Should be restricted to internal network only

TEST 5: S3 Bucket Public Access Control
--------
Objective: Check if unsigned requests can access objects or list bucket
Result: ✗ CRITICAL - PUBLIC BUCKET MISCONFIGURATION

5a. Unsigned object access (no query string signature)
  - Request: GET /users/{user-uuid}/{image-uuid}.png (no X-Amz-* params)
  - Response: HTTP 200 (SUCCESS - object publicly readable)
  - Private image accessible without AWS credentials
  - No authentication required for object retrieval

5b. Bucket root enumeration
  - HEAD /: HTTP 200 (bucket exists and exposes metadata)

5c. Bucket listing without credentials
  - GET /?list-type=2&max-keys=1: HTTP 200 (SUCCESS)
  - Response XML contains full bucket contents
  - Returned sample entry: "users/'/a5cebccb-38ec-4d85-bb6c-468875f9e686.png"
  - NextContinuationToken indicates more objects available
  - All user images enumerable without authentication

Findings:
  1. S3 bucket allows public list-bucket operation (critical)
  2. S3 objects lack encryption-at-rest controls or ACLs
  3. Any internet user can enumerate all uploaded images
  4. Any internet user can download all images without auth
  5. Business model (file sharing) undermined - images not private

TEST 7: TLS Cipher Enumeration (HTTPS 443)

Result: ✓ STRONG CONFIGURATION

Cipher Strength:

  - TLSv1.2 ciphers: ECDHE-ECDSA with AES/ARIA/CAMELLIA/ChaCha20
  - TLSv1.3 ciphers: AES-GCM and ChaCha20-Poly1305
  - Compression disabled (CRIME protection)

Finding: TLS configuration is strong; no cipher weaknesses

TEST 8: Security Headers (HTTPS root)
--------
Objective: Check presence of HSTS, CSP, Permissions-Policy headers
Result: ⚠️  MISSING CRITICAL HEADERS

Headers Present:
  ✓ X-Frame-Options: DENY (clickjacking protection)
  ✓ X-Content-Type-Options: nosniff
  ✓ X-XSS-Protection: 1; mode=block
  ✓ Referrer-Policy: strict-origin-when-cross-origin

Headers MISSING:
  ✗ Strict-Transport-Security (HSTS) - not set
  ✗ Content-Security-Policy (CSP) - not set
  ✗ Permissions-Policy - not set

Findings:
  1. HSTS header missing - browsers won't enforce HTTPS-only
  2. CSP missing - injection attacks not constrained by policy
  3. Browsers could downgrade to HTTP on next visit (HSTS needed)
