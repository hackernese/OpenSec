# Finding: Exposed Backend Application Server (Port 5000)
Severity: critical
CVSS: 9.8 (CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H)
Affected: 51.161.130.70:5000 (thedownundernews.online backend)
References: CWE-284 (Improper Access Control), OWASP A01:2021

Summary:
The Gunicorn backend application server is directly accessible on port 5000 without any authentication or access controls. This completely bypasses the nginx reverse proxy security layer, exposing administrative functionality and sensitive data.

Description:
During the assessment, it was discovered that the Python/Gunicorn backend server running on port 5000 is publicly accessible. While the nginx reverse proxy on ports 80/443 is intended to be the only entry point, the backend server accepts connections directly from the internet.

This exposure allows attackers to:
- Access the admin panel (/admin) without proxy-level restrictions
- Retrieve sensitive API data including admin credentials
- Bypass any rate limiting or access controls implemented at the proxy level
- Access internal endpoints not intended for public consumption

Evidence:
- Direct access to http://51.161.130.70:5000/ returns the full website
- http://51.161.130.70:5000/admin returns 200 OK (2,894 bytes)
- http://51.161.130.70:5000/api/articles exposes admin user details
- Server header confirms: "Server: gunicorn"

Business Impact:
Complete compromise of application security model. The multi-tier architecture is rendered ineffective as attackers can bypass all proxy-level security controls. This could lead to unauthorized administrative access, data theft, and system compromise.

Recommendation:
1. IMMEDIATE: Block port 5000 from public internet access using firewall rules (iptables/ufw)
2. Configure Gunicorn to listen only on localhost (127.0.0.1:5000)
3. Implement application-level authentication on all sensitive endpoints
4. Consider network segmentation to isolate backend services

# Finding: Anonymous FTP Access Enabled
Severity: high
CVSS: 7.5 (CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N)
Affected: 51.161.131.195:21 (media.thedownundernews.online)
References: CWE-284, CWE-552, OWASP A01:2021

Summary:
The FTP server on the media subdomain allows anonymous login, providing unauthenticated access to media files including documents and images.

Description:
The vsftpd 3.0.5 FTP server on the media server (51.161.131.195) permits anonymous authentication. Upon connecting with anonymous credentials, users gain read access to the FTP root directory containing media assets.

Files currently exposed:
- 37550846eae5457d93ddd8e1d2faeaca.html (76 bytes)
- 58e75939c3d24841806d3a069e919576.png (230,599 bytes)
- 66ea642847be4ef0a800fb8cb8432d79.png (167,268 bytes)
- d2273a1a2576489fb419cc1049c4c62f.pdf (624,807 bytes)

Additionally, all FTP communications occur in plaintext (unencrypted), exposing any credentials used to potential interception.

Evidence:
- nmap ftp-anon script confirms: "Anonymous FTP login allowed (FTP code 230)"
- FTP banner: "vsFTPd 3.0.5"
- Directory listing shows 4 files with read permissions

Business Impact:
Unauthorized access to media files that may contain proprietary content, internal documents, or sensitive information. The PDF file (624KB) is particularly concerning as it may contain business documents. Plaintext FTP also risks credential exposure if staff use authenticated sessions.

Recommendation:
1. Disable anonymous FTP access in vsftpd configuration (anonymous_enable=NO)
2. Migrate to SFTP (SSH-based file transfer) for encrypted communications
3. Implement proper authentication for all file access
4. Review exposed files for sensitive content and assess data breach implications
5. Consider removing FTP service entirely if not business-critical

# Finding: Admin Credentials Disclosed in API Response
Severity: high
CVSS: 7.5 (CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N)
Affected: https://thedownundernews.online/api/articles
References: CWE-200, CWE-359, OWASP A01:2021

Summary:
The public API endpoint exposes administrator account information including username, email address, role, and account creation timestamp.

Description:
The /api/articles endpoint returns article data that includes full author details. For articles authored by the administrator, this exposes:
- Username: admin
- Email: admin@thedownundernews.it.com
- Role: admin
- Account status: active
- Creation date: 2026-09-13T13:16:02.003617+00:00

This information disclosure provides attackers with valid usernames and email addresses for potential credential attacks, phishing, or social engineering.

Evidence:
- GET request to /api/articles returns JSON with author objects
- Author object contains: {"username": "admin", "email": "admin@thedownundernews.it.com", "role": "admin", "is_active": true}

Business Impact:
Exposure of admin credentials enables targeted attacks against administrative accounts. The email address can be used for spear-phishing, and the username confirms valid authentication targets for brute-force attempts.

Recommendation:
1. Implement API response filtering to exclude sensitive user fields
2. Create a separate "public profile" object with only necessary display information
3. Review all API endpoints for similar information disclosure
4. Consider implementing field-level access controls based on authentication status

# Finding: Missing HTTP Security Headers
Severity: medium
CVSS: 5.3 (CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N)
Affected: https://thedownundernews.online/, https://media.thedownundernews.online/
References: CWE-693, OWASP A05:2021

Summary:
The web application is missing critical HTTP security headers that protect against common web attacks including clickjacking, MIME-type sniffing, and protocol downgrade attacks.

Description:
Security header analysis revealed the following deficiencies:

Missing Headers:
- Strict-Transport-Security (HSTS): Not implemented - vulnerable to SSL stripping
- Content-Security-Policy (CSP): Not implemented - no XSS mitigation
- X-Content-Type-Options: Not implemented - MIME sniffing possible
- Referrer-Policy: Not implemented - referrer leakage
- Permissions-Policy: Not implemented - unrestricted browser features

Present but Suboptimal:
- X-Frame-Options: Present (deprecated, should use CSP frame-ancestors)
- Server: nginx (information disclosure)

Evidence:
- curl -sI https://thedownundernews.online/ shows only Server header
- No security headers present in response

Business Impact:
Without these protections, the application is more susceptible to:
- Man-in-the-middle attacks (no HSTS)
- Cross-site scripting exploitation (no CSP)
- Clickjacking attacks (deprecated X-Frame-Options only)
- Browser feature abuse (no Permissions-Policy)

Recommendation:
Add the following headers in nginx configuration:

```nginx
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload" always;
add_header Content-Security-Policy "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com; img-src 'self' data: https:; frame-ancestors 'none';" always;
add_header X-Content-Type-Options "nosniff" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Permissions-Policy "geolocation=(), microphone=(), camera=()" always;
```

# Finding: Missing HSTS on TLS Endpoints
Severity: medium
CVSS: 4.8 (CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:L/I:L/A:N)
Affected: https://thedownundernews.online/, https://media.thedownundernews.online/
References: CWE-319, OWASP A02:2021

Summary:
Neither web endpoint implements HTTP Strict Transport Security (HSTS), leaving users vulnerable to protocol downgrade and man-in-the-middle attacks.

Description:
While both domains support HTTPS with valid Let's Encrypt certificates and redirect HTTP to HTTPS, the absence of HSTS headers means:
- Browsers will still attempt initial HTTP connections
- Active network attackers can intercept and prevent the HTTPS redirect
- Users are vulnerable to SSL stripping attacks on untrusted networks

Both servers were confirmed to lack this header during SSL/TLS analysis using testssl.

Evidence:
- testssl output: "HSTS: NOT offered"
- curl -sI shows no Strict-Transport-Security header

Business Impact:
Users accessing the site from public WiFi, corporate networks, or compromised networks may have their sessions intercepted before the HTTPS redirect occurs, potentially exposing credentials or session tokens.

Recommendation:
1. Add HSTS header: Strict-Transport-Security: max-age=31536000; includeSubDomains
2. After confirming proper HTTPS operation, consider HSTS preloading
3. Ensure all subdomains also support HTTPS before adding includeSubDomains

# Finding: TLS CBC-Mode Ciphers Enabled (LUCKY13 Potential)
Severity: low
CVSS: 3.7 (CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:L/I:N/A:N)
Affected: https://thedownundernews.online/, https://media.thedownundernews.online/
References: CVE-2013-0169, CWE-310

Summary:
Both TLS endpoints support CBC-mode cipher suites which are theoretically vulnerable to the LUCKY13 timing attack.

Description:
SSL/TLS analysis revealed that both servers support TLS 1.2 cipher suites using CBC (Cipher Block Chaining) mode, including:
- ECDHE-ECDSA-AES128-SHA256
- ECDHE-ECDSA-AES256-SHA384

While modern TLS implementations include mitigations for LUCKY13, the presence of these ciphers represents a theoretical weakness. AEAD ciphers (GCM, ChaCha20-Poly1305) are preferred.

Evidence:
- testssl output: "LUCKY13 (CVE-2013-0169): potentially vulnerable (uses TLS CBC ciphers)"
- CBC ciphers listed but not preferred over AEAD alternatives

Business Impact:
Low practical impact due to attack complexity, but represents deviation from TLS best practices. Modern browsers will typically negotiate AEAD ciphers when available.

Recommendation:
1. Disable CBC-mode ciphers in nginx SSL configuration
2. Prioritize AEAD ciphers (GCM, ChaCha20-Poly1305) in cipher ordering
3. Example nginx configuration:
   ssl_ciphers 'ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305';

# Finding: Server Information Disclosure
Severity: low
CVSS: 3.1 (CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N)
Affected: All endpoints
References: CWE-200, OWASP A01:2021

Summary:
The web server and backend disclose software identification in HTTP response headers, aiding attackers in fingerprinting the technology stack.

Description:
HTTP response headers reveal:
- Main server: "Server: nginx"
- Backend: "Server: gunicorn"
- FTP server: "vsFTPd 3.0.5"

While version numbers are not fully disclosed for nginx, the software identification assists attackers in:
- Identifying potential version-specific vulnerabilities
- Tailoring exploits for the detected software
- Reducing reconnaissance effort

Evidence:
- curl -sI responses show Server headers
- FTP SYST command returns version information

Business Impact:
Minimal direct impact, but reduces the effort required for targeted attacks and contributes to the overall attack surface.

Recommendation:
1. Configure nginx: server_tokens off;
2. Configure Gunicorn to suppress server header or use nginx to strip it
3. Configure vsftpd: ftpd_banner=Welcome to FTP service (custom banner)

# Finding: Media Server Backend Unavailable (502 Bad Gateway)
Severity: info
CVSS: N/A
Affected: https://media.thedownundernews.online/
References: N/A

Summary:
The media subdomain returns HTTP 502 Bad Gateway errors, indicating a backend service failure.

Description:
All requests to media.thedownundernews.online return 502 errors from the nginx reverse proxy. This indicates the backend application server is either:
- Not running
- Misconfigured
- Unable to communicate with nginx

While not a security vulnerability per se, this represents an availability issue and may indicate infrastructure problems that could mask other security concerns.

Evidence:
- curl -sI https://media.thedownundernews.online/ returns HTTP/1.1 502 Bad Gateway
- Consistent across multiple test requests

Business Impact:
Media content is unavailable to users. If the subdomain was intended to serve media files, content delivery is impacted.

Recommendation:
1. Review backend service logs for the media subdomain
2. Ensure backend application is running and properly configured
3. Verify nginx upstream configuration points to correct backend address
