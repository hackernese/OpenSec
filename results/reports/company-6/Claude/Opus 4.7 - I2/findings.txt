# Finding: Unauthenticated Exposure of Confidential Client Data on Admin Dashboard
Severity: critical
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N (7.5)
Affected: https://ausecurity.best/dashboard.html , http://ausecurity.best:8080/dashboard.html
References: CWE-200 (Exposure of Sensitive Information), CWE-306 (Missing Authentication for Critical Function), OWASP A01:2021 Broken Access Control

Summary:
The internal admin dashboard page is served to anyone on the Internet without any authentication check at the server. The HTML itself is hardcoded with real-looking client company names, personal names, email addresses, business metrics (revenue, number of active clients), and an engagement activity log that discloses specific client-and-service combinations (for example, who received a penetration-test report or who had an ISO 27001 audit).

Description:
A GET request to https://ausecurity.best/dashboard.html returns HTTP 200 with the full admin UI (16,497 bytes) directly from the web server. The only "access control" is a client-side JavaScript check in /assets/js/main.js (isAuthenticated() → redirectToLogin()) which runs AFTER the HTML has already been delivered. Because the sensitive content is baked into the static HTML and not fetched post-auth, anyone with the URL can read it before the JavaScript runs, by disabling JavaScript, or simply by using curl / wget / View-Source. The same resource is also exposed on the plaintext HTTP port 8080 (nginx/1.25.5).

Confirmed hardcoded disclosures in the HTML body include:
  - Business metrics: "Total Enquiries: 47", "Active Clients: 12", "Assessments YTD: 19", "Open Proposals: 5", "Revenue YTD: $1.2M".
  - Client identities + contact emails of five organisations (Meridian Financial Solutions / James Hargreaves <james@meridianfs.com.au>, ShopStream Pty Ltd / Lara Whitfield <lara@shopstream.io>, Nexahealth Clinics / Mark Okonkwo <m.okonkwo@nexahealth.au>, Orion Logistics / Chen Wei <cwei@orionlogistics.com.au>, Starfield Technologies / Priya Nair <priya@starfieldtech.io>).
  - Engagement activity log tying individual clients to specific delivered services (e.g. "ISO 27001 audit completed — Meridian FS", "Pentest report delivered — ShopStream", "Contract signed — Orion Logistics GRC").

Business impact: For a GRC + penetration-testing consultancy, publicly disclosing client identities, engagement types, and revenue figures is a direct breach of client confidentiality, likely in conflict with every signed Non-Disclosure Agreement and with the Australian Privacy Act 1988 (APP 11) obligations around personal information. It also hands competitors a target list and gives attackers a highly curated phishing list of individuals who already trust AuSecurity.

Evidence stored under: evidence/t-api2/probe2.txt (full dashboard HTML dump).

Recommendation:
1. Enforce authentication SERVER-SIDE before the dashboard HTML is ever returned. In the nginx / backend configuration, require a valid session cookie (or JWT) for every request to /dashboard.html and respond with HTTP 302 to /login (not 200) when the session is absent or invalid.
2. Remove ALL hardcoded client PII, metrics, and activity entries from the HTML template. The page should render only a layout shell and fetch its content from authenticated API endpoints at runtime.
3. If a demo dashboard is desired for marketing, use clearly fictional data and place it on a separate, labelled page (e.g. /demo-dashboard.html).
4. Review and notify any clients whose details may have been exposed, in line with the Notifiable Data Breach scheme.
5. Audit for any Google / Bing / internet archive caching of the page content and request removal if indexed.

# Finding: Publicly Reachable osTicket Installation Wizard (Pre-Authentication System Takeover)
Severity: critical
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H (10.0)
Affected: https://ticket.ausecurity.best/setup/install.php , http://ticket.ausecurity.best:8080/setup/install.php
References: CWE-1188 (Insecure Default Initialization of Resource), CWE-284 (Improper Access Control), osTicket post-install hardening guide

Summary:
The osTicket installation wizard is still reachable without authentication on both the HTTPS (443) and plaintext HTTP (8080) ports of ticket.ausecurity.best. Any unauthenticated attacker can walk through the installer, point osTicket at an attacker-controlled database, and emerge as the admin of the ticketing system — which generally runs code as the web server user and ships customer support messages, attachments, and (often) credentials for integrations.

Description:
GET https://ticket.ausecurity.best/setup/install.php returns HTTP 200 with the interactive osTicket Installer page (title "osTicket Installer", 4,825 bytes), including a visible POST form with a hidden `s=prereq` field. The same page is identically reachable in plaintext over http://ticket.ausecurity.best:8080/setup/install.php. In addition, visiting the application root (https://ticket.ausecurity.best/) and the staff login (/scp/login.php) both HTTP 302 the browser to /setup/install.php, confirming that the osTicket deployment is in a "setup-not-finished" state and that the installer is the live front door.

The installer wizard, when completed by an attacker, allows them to:
  - choose or recreate the admin account (immediate privileged account takeover);
  - redirect the installation to a different MySQL/MariaDB server (data exfiltration path, and potential RCE via maliciously crafted DB callbacks);
  - import malicious plugins or language packs post-setup;
  - from the admin panel, upload server-side templates / signatures, often reachable as a path to remote code execution.

Service info disclosed by the installer response headers: osTicket v1.18.4, PHP/8.2.33, dual front-ends nginx/1.22.1 (443) and Apache/2.4.68 (8080). PHPSESSID cookies are set with no HttpOnly and no Secure flags (see separate finding).

Evidence stored under: evidence/t4-osticket-installer/install-443.html , install-8080.html; evidence/t10-nuclei/results-focused.txt (nuclei "osticket-installer" HIGH); evidence/t1-ports/stage2-services.nmap (NSE http-title "osTicket Installer").

Recommendation:
1. Immediately take ticket.ausecurity.best offline (or restrict access to a known admin IP via firewall / nginx `allow`/`deny`) until the installer is dealt with.
2. Complete the osTicket installation, then DELETE the entire /setup/ directory from the web root as the official osTicket post-install step requires.
3. Verify no residual files remain (/setup/install.php, /setup/*.php, /setup/images/, /setup/js/, /setup/css/).
4. Disable the plaintext HTTP service on port 8080 (Apache 2.4.68) or at minimum force an HTTPS redirect and apply the same /setup/ removal there.
5. Rotate any credentials / tokens that may have been configured in osTicket during this exposure window.
6. After cleanup, re-run a controlled vulnerability scan to confirm the installer is 404.

# Finding: Email Domain Trivially Spoofable (No SPF, DKIM, DMARC, or MX)
Severity: critical
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:C/C:L/I:H/A:N (8.1)
Affected: ausecurity.best (sender domain), info@ausecurity.best (advertised mailbox)
References: RFC 7208 (SPF), RFC 6376 (DKIM), RFC 7489 (DMARC), MITRE ATT&CK T1566.001 (Spearphishing Attachment)

Summary:
The ausecurity.best domain publishes no SPF record, no DMARC policy, no DKIM selectors, and no MX records. Any sender anywhere on the Internet can forge email with "From: anything@ausecurity.best" and most receiving mail systems will accept it. There is also no mailbox listening on the domain, so the "info@ausecurity.best" address advertised on the website cannot actually receive mail.

Description:
Direct DNS queries against 1.1.1.1 return:
  - MX ausecurity.best → (empty)
  - TXT ausecurity.best → (no SPF record)
  - TXT _dmarc.ausecurity.best → (no DMARC record)
  - TXT default._domainkey / google._domainkey / k1._domainkey / selector1._domainkey / selector2._domainkey / mail._domainkey / dkim._domainkey / smtp._domainkey → (all empty)
  - CAA ausecurity.best → (none)

Business impact for a security consultancy is especially severe:
  - An attacker can send a convincing phishing email purporting to be from a Director or a known consultant at AuSecurity to the business's actual clients (whose identities are already leaked publicly via the dashboard disclosure, see other finding). The receiving organisation has no DMARC signal to reject or quarantine the message.
  - Combined with the exposed client list and the DOM-based XSS and open-redirect on ausecurity.best (both separate findings), a highly convincing credential-harvesting campaign can be launched entirely under the "ausecurity.best" brand.
  - Advertised mailbox info@ausecurity.best cannot receive responses because no MX record exists; legitimate client enquiries that bounce may be perceived as unprofessional or as a sign of compromise.

Evidence stored under: evidence/t3-email/dns.txt.

Recommendation:
1. Publish a strict SPF record. If AuSecurity does not send any email at all from the domain, set `v=spf1 -all`. Otherwise, enumerate every legitimate sender (Google Workspace, Microsoft 365, SendGrid, etc.) and include them explicitly.
2. Publish a DMARC record on `_dmarc.ausecurity.best` starting with `v=DMARC1; p=reject; sp=reject; adkim=s; aspf=s; rua=mailto:dmarc-reports@ausecurity.best; fo=1`. Begin with `p=none` for a short monitoring window if there is uncertainty, then move to `p=reject`.
3. If the domain IS used for email: configure DKIM with 2048-bit keys on every sender (Google Workspace etc.), ensure the DKIM d= aligns with ausecurity.best, and enforce DMARC alignment strict.
4. If the domain is NOT used for email: publish an explicit "null MX" record (`ausecurity.best. 300 IN MX 0 .`) per RFC 7505, publish `v=spf1 -all`, publish a DKIM `*._domainkey.ausecurity.best. TXT "v=DKIM1; p="` (empty key) record, and remove info@ausecurity.best from the website; publish a working contact form or a different authenticated channel.
5. Publish a CAA record limiting certificate issuance to the specific CA(s) actually used (`0 issue "letsencrypt.org"`).

# Finding: Reflected DOM-based XSS on Consultation Success Page (name Parameter)
Severity: critical
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:C/C:H/I:H/A:L (9.3)
Affected: https://ausecurity.best/consultation-success.html (parameter `name`) , http://ausecurity.best:8080/consultation-success.html
References: CWE-79 (Improper Neutralization of Input in Web Page), OWASP DOM-based XSS Prevention Cheat Sheet

Summary:
The /consultation-success.html page reads the `name` query parameter from the URL and writes it directly into the DOM using `.innerHTML`, without sanitisation or encoding. An attacker-crafted URL under the trusted ausecurity.best domain will execute arbitrary JavaScript in the victim's browser. Because the application uses same-origin session cookies for its /api/auth/* endpoints, this is enough for session riding against any authenticated AuSecurity admin.

Description:
The HTML served from /consultation-success.html contains the following inline script (verbatim from the server response, lines 383–401 of the body):

    document.addEventListener('DOMContentLoaded', () => {
      const urlParams   = new URLSearchParams(window.location.search);
      const userName    = urlParams.get('name');
      const companyName = urlParams.get('company');
      if (userName) {
        document.getElementById('user-name').innerHTML = userName;   // <-- SINK
      } else {
        document.getElementById('user-name').textContent = 'there';
      }
      if (companyName) {
        document.getElementById('company-name').textContent = companyName;
      } else {
        const companyPart = document.getElementById('company-name').parentElement;
        companyPart.style.display = 'none';
      }
    });

The sink `element.innerHTML = userName` interprets any HTML (including <img onerror=…>, <svg onload=…>, <iframe srcdoc=…>) placed in the `name` parameter. Note that the `company` parameter uses the safer `.textContent`, confirming that the developer knows the difference — this is a mistake, not a framework limitation.

The success page is reachable WITHOUT first submitting the contact form, by simply visiting:
  https://ausecurity.best/consultation-success.html?name=<img%20src=x%20onerror=alert(1)>&company=X

The attacker payload executes with origin https://ausecurity.best, which gives it:
  - Full ability to read the DOM of the trusted site (defacement, keylogging on other open forms via same-origin iframes).
  - Ability to call fetch('/api/*', {credentials:'same-origin'}) — if a logged-in admin visits the link, the attacker can read the admin's data from /api/auth/me and trigger admin actions.
  - Ability to redirect the victim to an attacker-controlled login clone.
  - Credential theft via a fake "please re-authenticate" overlay rendered on the real domain.

The vulnerability is especially damaging in combination with the spoofable ausecurity.best email domain (see separate finding) — a phishing email purportedly from AuSecurity, containing a link to the attacker's XSS URL under the real ausecurity.best domain, is extremely likely to be clicked.

Evidence stored under: evidence/t-finalprobe/final2.txt (full HTML body with the vulnerable script).

Recommendation:
1. Replace `.innerHTML = userName` with `.textContent = userName`. This is a one-line fix and preserves the existing display intent (plain text name).
2. Add server-side output encoding and server-side validation of the `name` and `company` parameters on this and every page that reflects user input.
3. Add a strict Content-Security-Policy to ausecurity.best that at minimum sets `default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'self';` — this would have broken this specific attack even without changing the vulnerable code.
4. Grep the entire frontend codebase for other uses of `.innerHTML =`, `document.write`, and template interpolation and apply the same fix.

# Finding: Client-Side Open Redirect on Login Flow
Severity: high
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:C/C:L/I:L/A:N (6.1)
Affected: https://ausecurity.best/login.html (and /login) — handler in /assets/js/main.js
References: CWE-601 (URL Redirection to Untrusted Site), OWASP ASVS V5.1.5

Summary:
After a successful login, the JavaScript handler blindly navigates the browser to whatever URL was supplied in the `redirect` query-string parameter, with no origin or scheme check. The comment above the code even claims "Safety check: only allow same-origin redirects" but the check is not implemented. Any attacker-controlled URL is accepted, enabling phishing campaigns that redirect through the real ausecurity.best login page.

Description:
Relevant excerpt from https://ausecurity.best/assets/js/main.js (verbatim from the server):

    if (res.ok) {
      const params = new URLSearchParams(window.location.search);
      const redirect = params.get('redirect');
      // Safety check: only allow same-origin redirects
      if (redirect) {
        window.location.href = redirect;         // <-- NO VALIDATION PERFORMED
      } else {
        window.location.href = '/dashboard';
      }
    }

A victim clicking a link like `https://ausecurity.best/login?redirect=https://evil.example/aus-login-session-expired` will:
  1. See the real AuSecurity login page under the real HTTPS AuSecurity domain.
  2. Submit real credentials to the real backend.
  3. On success, be redirected to the attacker-controlled site which can present a pixel-perfect "session expired, please re-enter your password" prompt or deliver malware.

Impact drivers:
  - This is particularly effective combined with the spoofable email domain (no SPF/DMARC/DKIM), the exposed client list (dashboard disclosure), and the self-signed TLS cert training users to click past warnings.
  - The server-side `/login?redirect=` endpoint itself does NOT emit a 3xx with a Location header (we confirmed HTTP 200 with no Location on the first query); the vulnerability is strictly on the client side after a 200 OK /api/auth/login response.

Evidence stored under: evidence/t-api2/probe2.txt (main.js source).

Recommendation:
1. Actually implement the "same-origin" check promised in the comment. For example:
      const url = new URL(redirect, window.location.origin);
      if (url.origin !== window.location.origin) {
        window.location.href = '/dashboard';
      } else {
        window.location.href = url.pathname + url.search + url.hash;
      }
2. Even better, keep the redirect state server-side (opaque token mapped to a path) rather than echoing it from the URL.
3. Add a server-side allow-list and strip the `redirect` parameter when the login endpoint returns the login page.
4. Combine with CSP `frame-ancestors 'self'` and `Referrer-Policy: strict-origin-when-cross-origin` to reduce residual phishing utility.

# Finding: Self-Signed TLS Certificate with CA:TRUE on Primary Website
Severity: high
CVSS: CVSS:3.1/AV:N/AC:H/PR:N/UI:R/S:C/C:H/I:H/A:N (7.4)
Affected: https://ausecurity.best:443 (apex), nginx/1.22.1
References: CWE-295 (Improper Certificate Validation), CA/Browser Forum Baseline Requirements, Mozilla CA policy

Summary:
The TLS certificate presented by the apex website is self-signed. All major browsers will show a full-page interstitial warning ("Your connection is not private" / "NET::ERR_CERT_AUTHORITY_INVALID") when a visitor opens https://ausecurity.best/. The certificate is additionally marked as a Certificate Authority (`CA:TRUE`) in its Basic Constraints, which is incorrect for a leaf certificate. For a security consultancy, serving an untrusted certificate at the brand's primary web presence is both a credibility problem and a real security problem because it conditions visitors to ignore browser warnings.

Description:
openssl / nmap ssl-cert output confirms:
  Subject    : CN=ausecurity.best
  Issuer     : CN=ausecurity.best           (self-issued → self-signed)
  SAN        : DNS:ausecurity.best
  Not before : 2026-09-14T15:32:18Z
  Not after  : 2027-09-14T15:32:18Z          (1 year, atypical for a self-signed cert)
  Key        : RSA 2048-bit
  Signature  : sha256WithRSAEncryption
  SHA256 fp  : B5:30:10:E0:32:E7:42:10:E4:B1:F0:68:A0:C5:B2:A2:0B:F6:44:C1:F3:32:92:87:4D:1C:64:07:14:8D:14:E2
  Basic constraints: CA:TRUE   <-- ABNORMAL FOR A LEAF CERT

Impact:
  - Every normal visitor sees a browser interstitial and either (a) abandons the site, (b) clicks through, training themselves and clients to ignore TLS warnings. This is destructive to a security brand.
  - The CA:TRUE flag means an attacker who ever obtains the certificate's private key could issue arbitrary subordinate certificates in that chain and present them in man-in-the-middle attacks against anyone who had chosen to "always trust" the AuSecurity cert in their trust store.
  - Subdomains blog.* and ticket.* correctly use Let's Encrypt certificates (CN=YE1, EC P-256). The misconfig is specific to the apex.

Evidence stored under: evidence/t1-ports/stage2-services.nmap , evidence/t2-tls/ssl-nse.nmap , evidence/enum-001/* .

Recommendation:
1. Obtain a trusted certificate from a public CA (Let's Encrypt is already in use for the subdomains and is free; HTTP-01 or DNS-01 works). Install for ausecurity.best (apex) and www.ausecurity.best.
2. Automate renewal (certbot timer / acme.sh cron).
3. Publish a CAA record restricting issuance to the chosen CA(s): `ausecurity.best. CAA 0 issue "letsencrypt.org"`.
4. Remove the current self-signed cert and the CA:TRUE basic constraint.
5. Enable HSTS (`Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`) and submit to the HSTS preload list once stable.

# Finding: WordPress Admin Username Enumeration via REST API and Author Redirect
Severity: high
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N (5.3)
Affected: https://blog.ausecurity.best/
References: CWE-204 (Observable Response Discrepancy), WordPress REST API users endpoint

Summary:
The WordPress REST API at /?rest_route=/wp/v2/users and /?rest_route=/wp/v2/users/1 returns unauthenticated JSON that identifies the administrator account by username and slug (`admin`), along with the author permalink and gravatar hash. The `?author=1` → 301 redirect also leaks the slug. Both are standard precursors to targeted credential attacks (brute-force, password reuse, credential stuffing) against the known admin username.

Description:
Confirmed enumeration vectors:
  1. GET https://blog.ausecurity.best/?rest_route=/wp/v2/users
       → HTTP 200 JSON array containing {id:1, name:"admin", slug:"admin",
         link:"https://blog.ausecurity.best/index.php/author/admin/",
         avatar_urls:{..., gravatar_hash: "25e5434e5d0e1a62822d3670d4cf46e6b59a88908848f9bb1c91d11c819aa61b"}}
  2. GET https://blog.ausecurity.best/?rest_route=/wp/v2/users/1
       → HTTP 200 JSON with the same admin data.
  3. GET https://blog.ausecurity.best/?author=1
       → HTTP 301 Moved Permanently with Location containing "/author/admin/".
  4. The direct `/wp-json/wp/v2/users` endpoint is blocked (404), but the `?rest_route=` fallback (which WordPress enables when permalinks are not configured for the API) is not — so the mitigation is incomplete.

The gravatar hash additionally allows an attacker to confirm the admin's registered email across the public Gravatar database if the user is a Gravatar member, extending the identity disclosure beyond just the username.

Evidence stored under: evidence/t6-wordpress/manual-probes.txt , evidence/t-api2/probe2.txt , evidence/t10-nuclei/results-focused.txt (nuclei "wp-user-enum" LOW).

Recommendation:
1. In WordPress, filter the REST API `/wp/v2/users` endpoint to require `edit_users` capability for anonymous callers. Can be done with a `rest_authentication_errors` or `rest_endpoints` filter in a mu-plugin.
2. Disable the `?rest_route=` fallback by configuring permalinks and enforcing routing so the only REST entry point is `/wp-json/*`, which is already 404.
3. Disable WordPress author archive URLs (`?author=N` redirect) via a `template_redirect` hook that 404s unauthenticated requests.
4. Rename the admin account from "admin" to a non-guessable value. Add a secondary account as the user-facing writer with no admin rights.
5. Enforce 2FA on all WordPress admins (plugin: Two-Factor, Wordfence, etc.).
6. Confirm that the WordPress login page is also protected by rate limiting and/or a CAPTCHA.

# Finding: WordPress XML-RPC Enabled with Pingback / User-Enumeration Methods
Severity: high
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:L/A:L (6.3)
Affected: https://blog.ausecurity.best/xmlrpc.php
References: CWE-918 (SSRF), CWE-307 (Improper Restriction of Excessive Authentication Attempts), CVE-2013-0235 (pingback DDoS pattern)

Summary:
The XML-RPC endpoint on the WordPress blog is enabled and advertises 82+ methods, including `pingback.ping` (SSRF / amplified-DoS vector), `wp.getUsersBlogs`, `wp.getAuthors`, `metaWeblog.getUsersBlogs`, and `system.multicall` (brute-force amplification). The endpoint responds correctly to a benign method call (demo.sayHello → "Hello!"), confirming it is live and processing requests.

Description:
Observed behaviour:
  - GET https://blog.ausecurity.best/xmlrpc.php → HTTP 405 Method Not Allowed (expected; XML-RPC accepts POST).
  - POST text/xml with `system.listMethods` → HTTP 200 OK, 82 method names returned, including `pingback.ping`, `pingback.extensions.getPingbacks`, `wp.getUsersBlogs`, `metaWeblog.getUsersBlogs`, `blogger.getUserInfo`, `wp.getAuthors`, `system.multicall`, `system.listMethods`, `demo.sayHello` (which returned "Hello!").
  - X-Pingback: https://blog.ausecurity.best/xmlrpc.php header is advertised on content pages.

Attack scenarios:
  - `pingback.ping` can be abused to make the WordPress server fetch arbitrary attacker-chosen URLs (SSRF against internal services on 51.79.167.208 or the OVH internal network). Historically it has also been used for amplified DDoS.
  - `system.multicall` lets an attacker pack dozens of `wp.getUsersBlogs` authentication attempts into a single HTTP request, bypassing simple rate-limit heuristics; combined with the known admin username this materially lowers brute-force cost. (Note: Our methodology forbade brute force; we did not test credentials.)
  - User-enumeration methods confirm individual usernames exist / do not exist by error-message differentiation.

Evidence stored under: evidence/t6-wordpress/manual-probes.txt (listMethods response, demo.sayHello proof), evidence/t-webprobe/webprobe.txt.

Recommendation:
1. If XML-RPC is not required by any plugin, disable it entirely:
     - Add `add_filter('xmlrpc_enabled', '__return_false');` in a mu-plugin, AND
     - At the web-server level, block POST to /xmlrpc.php with an Apache `<Files xmlrpc.php> Require all denied </Files>` or equivalent.
2. If XML-RPC is required (e.g. legacy Jetpack flows), restrict it to known partner IPs at the web-server level, and specifically disable `pingback.*` methods via the `xmlrpc_methods` filter.
3. Remove the `X-Pingback` header via the `wp_headers` filter.
4. Combine with rate limiting on the WAF / nginx for /xmlrpc.php (e.g. 5 requests per minute per IP).

# Finding: PHPSESSID Session Cookie Missing HttpOnly and Secure Flags
Severity: medium
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:U/C:H/I:L/A:N (7.1)
Affected: https://ticket.ausecurity.best/* , http://ticket.ausecurity.best:8080/* (osTicket)
References: CWE-1004 (Sensitive Cookie Without HttpOnly), CWE-614 (Sensitive Cookie Without Secure), OWASP ASVS V3.4

Summary:
The PHPSESSID session cookie set by the osTicket application has neither the HttpOnly nor the Secure attribute. Any client-side script that runs in the osTicket origin can read the session cookie (session theft via XSS), and the cookie is additionally transmitted in cleartext when the user hits the port-8080 HTTP mirror.

Description:
Observed Set-Cookie headers (verbatim) include:
  Set-Cookie: PHPSESSID=1498870558d9b2068a011152394bc681; path=/
  Set-Cookie: PHPSESSID=65d8bde750a84975f5af5d4a258a3232; path=/

nmap NSE http-cookie-flags explicitly reports `httponly flag not set`. The cookie is set without `Secure`, without `HttpOnly`, and without `SameSite`. On port 8080 the cookie is additionally delivered over cleartext HTTP (see separate HTTP-mirror finding).

Impact: once an attacker finds any XSS in osTicket (or in any content served from the ticket subdomain), they can read `document.cookie` and silently hijack the admin's session. On port 8080 the cookie is observable to any on-path attacker.

Evidence stored under: evidence/t2-tls/ssl-nse.nmap , evidence/t4-osticket-installer/install-*.html , evidence/t-finalprobe/nikto-ticket.txt.

Recommendation:
1. In the osTicket php.ini (or `ini_set` in a bootstrap file), set:
     session.cookie_httponly = 1
     session.cookie_secure   = 1
     session.cookie_samesite = Strict          (or Lax if cross-site navigations are needed)
     session.use_only_cookies = 1
     session.use_strict_mode  = 1
2. Regenerate session IDs on login (`session_regenerate_id(true)`) to defeat fixation.
3. Disable the port-8080 HTTP mirror (see separate finding) so the Secure flag can actually be enforced.
4. After rotation, invalidate all currently issued PHPSESSID values.

# Finding: Missing HTTP Security Headers on All Three Web Assets
Severity: medium
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:U/C:L/I:L/A:N (5.4)
Affected: https://ausecurity.best/ , https://blog.ausecurity.best/ , https://ticket.ausecurity.best/ (and the port-8080 mirrors)
References: OWASP Secure Headers Project, Mozilla Observatory

Summary:
The apex, blog, and ticket sites do not emit Strict-Transport-Security, Content-Security-Policy, X-Content-Type-Options, Referrer-Policy, or Permissions-Policy on their primary pages. X-Frame-Options is also missing on the apex and ticket; the WordPress blog does send a modest X-Frame-Options: SAMEORIGIN and a very narrow CSP (`frame-ancestors 'self'`). Properly configured, these headers would have independently blunted the DOM-based XSS, open-redirect, and SSL-stripping attacks already identified in this report.

Description:
HTTP response-header matrix (confirmed via curl and nmap http-security-headers NSE):

  Header                          | apex :443 | apex :8080 | blog :443      | ticket :443 | ticket :8080
  --------------------------------+-----------+------------+----------------+-------------+-------------
  Strict-Transport-Security       | missing   | N/A        | missing        | missing     | N/A
  Content-Security-Policy         | missing   | missing    | frame-ancestors| missing     | missing
  X-Frame-Options                 | missing   | missing    | SAMEORIGIN     | missing     | missing
  X-Content-Type-Options          | missing   | missing    | missing        | missing     | missing
  Referrer-Policy                 | missing   | missing    | strict-origin* | missing     | missing
  Permissions-Policy              | missing   | missing    | missing        | missing     | missing

(* strict-origin-when-cross-origin on blog)

Impact: these headers are low-cost defence-in-depth that would have significantly reduced the exploitability of several higher-severity findings (DOM XSS, open-redirect, SSL-stripping, clickjacking).

Evidence stored under: evidence/t2-tls/ssl-nse.nmap , evidence/t-finalprobe/nikto-*.txt .

Recommendation:
Apply the following minimum header set at the nginx / Apache layer on all three sites (tune CSP per actual needs):

  Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
  Content-Security-Policy:   default-src 'self'; img-src 'self' data: https://fonts.gstatic.com; style-src 'self' https://fonts.googleapis.com 'unsafe-inline'; font-src 'self' https://fonts.gstatic.com; script-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'self'; form-action 'self'
  X-Frame-Options:           DENY
  X-Content-Type-Options:    nosniff
  Referrer-Policy:           strict-origin-when-cross-origin
  Permissions-Policy:        camera=(), microphone=(), geolocation=(), interest-cohort=()
  Cross-Origin-Opener-Policy: same-origin
  Cross-Origin-Resource-Policy: same-origin

Then validate on Mozilla Observatory and address any remaining A/B-grade recommendations.

# Finding: WordPress Uploads Directory Listing Enabled
Severity: medium
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N (5.3)
Affected: https://blog.ausecurity.best/wp-content/uploads/
References: CWE-548 (Exposure of Information Through Directory Listing)

Summary:
Apache serves a browsable directory index at /wp-content/uploads/ on the WordPress blog, listing the yearly/monthly folders that WordPress creates and (recursively) every file ever uploaded. Even if no sensitive files are currently indexed, this is a persistent reconnaissance vector that will leak draft media, private attachments, and backup artefacts the moment they are placed under /wp-content/uploads/.

Description:
GET https://blog.ausecurity.best/wp-content/uploads/ returns HTTP 200 with an auto-generated Apache "Index of /wp-content/uploads" listing. Observed indexed child: `2026/` folder. The behaviour is confirmed by both the WPScan output and manual curl probes.

Evidence stored under: evidence/t6-wordpress/manual-probes.txt , evidence/t6-wordpress/wpscan.txt.

Recommendation:

3. Verify that no media files under /wp-content/uploads/ contain sensitive customer data (invoices, exported reports). If any do, move them out of the public uploads path and serve them through an authenticated download endpoint.

# Finding: Contact Form Lacks Rate Limiting and Message Length Validation
Severity: medium
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:L/A:L (5.4)
Affected: POST https://ausecurity.best/api/contact
References: CWE-770 (Allocation of Resources Without Limits or Throttling), CWE-20 (Improper Input Validation), OWASP ASVS V5.1.3

Summary:
The public /api/contact endpoint accepts an unlimited number of submissions per source IP in rapid succession, and it accepts message bodies at least 10,000 characters long without rejection. This is sufficient to abuse the ticketing/mail backend for log flooding, storage exhaustion, operator-mailbox denial-of-service, and (if forwarded to a client-facing CRM) to inject disruptive content.

Description:
Observations from the final probe (benign test marker payloads only):
  1. Five back-to-back POST /api/contact requests all returned HTTP 200 within ~1.1s each. No HTTP 429, no delay, no CAPTCHA.
  2. A 10 KB `message` body was accepted with HTTP 200.
  3. The successful response reflects the submitted `full_name` into a `redirect_url` field: `/consultation-success.html?name=<URL-encoded-name>&company=<company>` — this is the entry point for the related DOM-XSS finding.
  4. A honeypot `h` field IS correctly enforced (missing-field submissions get HTTP 422 "Field required") — this is the only existing anti-abuse mechanism and is defeatable by any human attacker.

Impact: without rate limiting an attacker (or a worm leveraging the no-SPF-DMARC spoofability) can submit thousands of enquiries per minute, overwhelming the back-office inbox or CRM queue; this effectively denies service to real leads and may be used to bury a targeted phishing lead among noise.

Evidence stored under: evidence/t-finalprobe/final.txt (benign markers tagged "AUSEC-TEST-20261005").

Recommendation:
1. Apply a per-IP rate limit at the nginx or application layer (e.g. 5 requests / minute / IP, with a short-term burst allowance).
2. Enforce server-side maximum lengths on every field: full_name ≤ 100 chars, company_name ≤ 150, email RFC5321 (254), phone ≤ 30, service_interest from an enum, message ≤ 2000 chars.
3. Add a server-side CAPTCHA or Turnstile check for anonymous submissions, in addition to the existing honeypot `h` field.
4. Log the source IP, user-agent, and timestamp of every submission to allow detection of abuse.
5. Note the benign test submissions tagged "[CLAWSEC AUTHORIZED PENTEST]" / marker "AUSEC-TEST-20261005" and delete them from the ingestion queue.

# Finding: osTicket web.config File Exposed

# Finding: Verbose Server Version Headers Across All Three Web Assets
Severity: low
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N (5.3)
Affected: ausecurity.best (nginx/1.22.1, nginx/1.25.5), blog.ausecurity.best (Apache/2.4.68), ticket.ausecurity.best (nginx/1.22.1, Apache/2.4.68, PHP/8.2.33)
References: CWE-200 (Exposure of Sensitive Information)

Summary:
Every HTTP response from the three in-scope sites discloses the exact web-server version (and, on the ticket host, the PHP minor version via X-Powered-By). This lets attackers skip the fingerprinting step and go directly to CVE lookup. Suppressing the version number does not fix the underlying software but materially raises the bar for mass-exploitation worms.

Description:
Observed headers:
  https://ausecurity.best/        : Server: nginx/1.22.1
  http://ausecurity.best:8080/    : Server: nginx/1.25.5
  https://blog.ausecurity.best/   : Server: Apache/2.4.68 (Debian)
  https://ticket.ausecurity.best/ : Server: nginx/1.22.1 ; X-Powered-By: PHP/8.2.33
  http://ticket.ausecurity.best:8080/ : Server: Apache/2.4.68 (Debian) ; X-Powered-By: PHP/8.2.33

Nikto additionally flagged nginx/1.22.1 and nginx/1.25.5 as "outdated". We did NOT confirm any specific exploitable CVE in these specific versions during this engagement — reduction here is defence-in-depth, not a direct exploit.

Evidence stored under: evidence/t1-ports/stage2-services.nmap , evidence/t-finalprobe/nikto-*.txt .

Recommendation:
1. nginx: add `server_tokens off;` globally in nginx.conf. For full version-string removal install nginx-extras + the Headers More module and `more_clear_headers 'Server';`.
2. Apache: add `ServerTokens Prod` and `ServerSignature Off` in the main config.
3. PHP: in php.ini set `expose_php = Off` to drop the X-Powered-By header.
4. Independently of the version-string change, plan an upgrade cycle: nginx mainline 1.27+, keep Apache on the current Debian security track, keep PHP on a maintained 8.3+ branch when available.
