# Finding: AWS Access Key and Secret Key publicly exposed in /js/awsvalid.js
Severity: critical
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H
Affected: https://imagesharer.xyz/js/awsvalid.js
References:
- CWE-798 Use of Hard-coded Credentials
- CWE-540 Inclusion of Sensitive Information in Source Code
- OWASP A02:2021 Cryptographic Failures

Summary:
A publicly reachable JavaScript file served by the application contains a valid AWS Access Key ID and Secret Access Key in plain text. The access key is the same one used by the back-end to generate pre-signed S3 URLs for the application, confirming the credentials are live production credentials with real access to the business's AWS account and user data.

Description:
The URL https://imagesharer.xyz/js/awsvalid.js (reachable without any authentication) contains the following block at the top of the file:

    /*
    AKIAQHQ6PGM62T2FFPGU
    c7njNpv1oT3rhBhUHue2e2d+oIFnw7QDgCmTtPCG
    ap-southeast-2
    */

The access key ID `AKIAQHQ6PGM62T2FFPGU` is identical to the AWS Access Key observed in every pre-signed URL produced by the live application (for example, in the response to GET /images/<uuid>). This confirms the key is active and is being used by the production backend to sign S3 requests.

Any person who views the application in a browser (or discovers the file through directory enumeration, archive.org, source-map leaks, or a search engine) obtains full access to whatever S3 bucket(s), and potentially any other AWS service, this IAM principal is authorized for. Based on observed behavior at least the `filesharer-research` bucket (ap-southeast-2) is in reach, which stores every user image. Depending on how the IAM policy was scoped, this could additionally allow:

- download, modification, replacement or deletion of every uploaded user image
- impersonation of the application (uploads under any user path)
- discovery and manipulation of the second observed bucket `imagesharer` (ap-northeast-1)
- any additional service calls the IAM policy permits (STS GetCallerIdentity, EC2, IAM, DB, etc.)

Business impact:
- Full compromise of customer image storage (confidentiality + integrity + availability)
- Potential full compromise of the AWS account
- Regulatory and reputational damage from mass data exposure
- No evidence of use is required to establish the breach — public disclosure is the breach

Recommendation:
1. Treat the keys as compromised. In the AWS console disable (deactivate) the key `AKIAQHQ6PGM62T2FFPGU` immediately, then delete it after confirming no production system still relies on it.
2. Rotate to a new key and store it only in a server-side secret manager (AWS Secrets Manager / IAM instance role / environment variable managed by a secrets system). Credentials must never be present in files that are served to a browser or committed to source control.
3. Audit CloudTrail for any use of the exposed key by IPs other than the application servers over the entire exposure window.
4. Scope the new IAM policy to the minimum necessary actions and the specific bucket + key prefix (least privilege). Deny `s3:*` cross-bucket. Deny `iam:*`, `sts:AssumeRole`, and administrative permissions.
5. Remove the file `/js/awsvalid.js` from the deployed application entirely; it has no legitimate client purpose.
6. Add a build/CI secret-scanning step (e.g. gitleaks, trufflehog) that fails the build when credentials are detected in public assets.

# Finding: Public S3 bucket (filesharer-research) with anonymous List and Read
Severity: critical
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:N/A:N
Affected:
- https://filesharer-research.s3.ap-southeast-2.amazonaws.com/
References:
- CWE-284 Improper Access Control
- OWASP A01:2021 Broken Access Control
- AWS: S3 Block Public Access best practice

Summary:
The S3 bucket that stores all user-uploaded images on behalf of imagesharer.xyz is open to the public internet for both anonymous bucket listing and anonymous object read. Every image a user uploads to the application — including those marked "private" inside the application — is in practice world-readable at a predictable URL. Signed URLs issued by the application therefore provide no confidentiality.

Description:
Direct, unauthenticated requests to the bucket succeed:

- `GET https://filesharer-research.s3.ap-southeast-2.amazonaws.com/?list-type=2` returns `200 OK` with a full XML enumeration of every object in the bucket (37 objects observed, 1000 object max per page); the complete list of user UUIDs and image UUIDs is exposed.
- `GET https://filesharer-research.s3.ap-southeast-2.amazonaws.com/users/<user-uuid>/<image-uuid>.jpg` returns `200 OK` with the raw image bytes and does NOT require any AWS SigV4 signature or query-string token.

The application layer generates short-lived pre-signed URLs (15 minutes for "private" images, 7 days for "public" images) and enforces web-side ownership checks on `/images/<uuid>` — but these controls are irrelevant because the bucket itself serves the same objects to anyone over anonymous HTTPS.

Secondary findings observed in the public listing:

- A key `users/'/a5cebccb-38ec-4d85-bb6c-468875f9e686.png` demonstrates that an attacker has previously supplied `'` as the `user_id` form field; the storage path was built from attacker-controlled input without sanitization.
- A key `users/00000000-0000-0000-0000-000000000000/...` suggests an unauthenticated-user default UUID was accepted and persisted.

Business impact:
- Mass confidentiality breach of every image ever uploaded, past and future
- Full enumeration of all user accounts via the storage layer (user UUIDs are keys)
- Regulatory exposure (privacy regulations typically treat user uploads as PII if faces/identifiers are present)
- The "private" visibility feature advertised in the application is deceptive to end users

Recommendation:
1. Enable "Block all public access" on the bucket (`filesharer-research`) at the account and bucket level immediately.
2. Remove any `s3:ListBucket` and `s3:GetObject` statements granted to `Principal: "*"` in the bucket policy and ACL. The bucket owner ID visible in listings (`39f9375616d183ed...`) is a canonical ID that can be checked in the console.
3. Serve all image reads through the application layer only, continuing to use short-lived pre-signed URLs — but now backed by a bucket that denies anonymous access.
4. Review every existing object to decide whether it must be re-issued under a new key (image UUID or storage path change) because the current UUIDs have been fully enumerated by third parties already.
5. Repeat the same hardening on any sibling bucket (the Tokyo bucket `imagesharer` was observed and appears already-locked-down; confirm its policy matches).

# Finding: Broken Object Level Authorization (BOLA) on image upload — attacker can upload images into any other user's account
Severity: high
CVSS: CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:H/A:N
Affected: POST https://imagesharer.xyz/images/upload
References:
- CWE-639 Authorization Bypass Through User-Controlled Key
- OWASP API1:2023 Broken Object Level Authorization
- OWASP A01:2021 Broken Access Control

Summary:
The image upload endpoint reads the owner UUID from a hidden `user_id` form field sent by the client instead of the authenticated session. An authenticated attacker can set this field to any other user's UUID (which is enumerable from the public S3 bucket) and have their uploaded image recorded against that user's account.

Description:
The upload form includes:

    <input type="hidden" name="user_id" value="<the-current-user's-uuid>">

The server trusts the submitted `user_id` as-is. A test registered account A (`740532d8-b0f3-4cad-a69a-43a0de29a4c8`) submitted a benign JPEG with the form field `user_id=0d542b4a-75de-4dc5-ac0b-35fed0279387` (account B). The server responded `302 Found` → `/images/fb7b20b2-3743-4824-b119-461501096203`. Account B's dashboard subsequently showed the image as if B had uploaded it; account A did not see it. The storage object was written to `users/0d542b4a-75de-4dc5-ac0b-35fed0279387/fb7b20b2-....jpg` on S3.

Observed detail that confirms the root cause: when the `user_id` field is removed, the backend throws `Undefined array key "user_id" in /var/www/html/src/UI/ImagesUiController.php:42` — meaning the controller never falls back to the authenticated session user; it strictly requires and trusts the client-sent field.

Chaining:
- Combined with the lack of CSRF protection (separate finding), the attacker can plant images under any user's account using a malicious page that posts cross-origin while the victim is logged in.
- Combined with the public S3 bucket, the attacker already knows every valid user_id to target.
- Combined with the loose file-upload validation (double-extension accepted; separate finding), the attacker can plant content with hostile filenames or embedded payloads under a victim's name.

Business impact:
- Attribution attack: an attacker can plant arbitrary (and potentially illegal or compromising) imagery under a victim's account, exposing the victim to legal action, abuse reports, or storage-quota abuse.
- Reputational damage to the service once the behaviour is public (any user can upload "as" another user).
- Loss of integrity for the entire image dataset — the "who uploaded this" field can no longer be trusted for any purpose, including moderation, forensics, or deletion-of-user-data responses.

Recommendation:
1. In `ImagesUiController.php` (around line 42) and in `ImagesService.php` (around line 71), ignore any client-supplied `user_id` and read the owner UUID exclusively from the authenticated session (e.g., `$_SESSION['user_id']`).
2. Remove the hidden `user_id` field from the upload form; it serves no purpose and signals a trust boundary error.
3. Review all other POST handlers for the same pattern (profile avatar POST, any API endpoint). The avatar upload POST does not expose this field, but the server-side logic should be audited to confirm it also derives owner from the session.
4. Delete all images uploaded during the exposure window that cannot be attributed with confidence to the session user they live under; audit the `users/'/` key and the `users/00000000-.../` keys which indicate the controller previously accepted attacker-supplied strings.

# Finding: Cross-site request forgery (CSRF) on all state-changing endpoints (upload, avatar upload, logout, registration)
Severity: high
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:U/C:N/I:H/A:L
Affected:
- POST https://imagesharer.xyz/register
- POST https://imagesharer.xyz/images/upload
- POST https://imagesharer.xyz/profile/avatar
- POST https://imagesharer.xyz/logout
References:
- CWE-352 Cross-Site Request Forgery (CSRF)
- OWASP A01:2021 Broken Access Control

Summary:
None of the application's state-changing POST endpoints include an anti-CSRF token or validate Origin / Referer headers. Any website a logged-in Imager user visits can silently perform these actions on their behalf, including uploading images into their account (and, combined with the BOLA finding above, into any other user's account), replacing their avatar, logging them out, or triggering registration flows.

Description:
Observed evidence:

- The `/register` and `/images/upload` forms were inspected in the live HTML; no `<input type="hidden" name="csrf_token">` or equivalent is present.
- A `curl` POST to `/images/upload` with `Origin: https://evil.example` and `Referer: https://evil.example/attack.html` succeeded (`HTTP/1.1 302 Found` → `/images/aa2821aa-3bd6-4aa4-813f-04c07c7e3567`), confirming the server does not check these headers.
- `/logout` was successfully triggered cross-origin (same curl pattern) — the session was invalidated and the subsequent `/dashboard` request returned `302` to `/login`.
- `/profile/avatar` has the same pattern (multipart upload, cookie-authenticated, no token).
- The `SameSite=Lax` default would normally mitigate top-level form POSTs for session cookies — but the PHPSESSID cookie here is not marked `SameSite` at all (see cookie-flags finding), so Lax does not apply.

Business impact:
- An attacker-controlled webpage can mutate any victim's state.
- Chained with the BOLA upload finding, an attacker can serve a visited page that silently uploads a chosen file (including malicious images or policy-violating content) under any other user they name — devastating for a photo-sharing platform.
- The combination allows "mass drive-by" attacks on the user base through a single compromised ad network or forum post.

Recommendation:
1. Add a per-session CSRF token to every state-changing form, bound to the session, and validate it server-side on every POST, DELETE, PATCH, and PUT. Reject requests whose token is missing or mismatched.
2. Add origin/referer validation as defense-in-depth: reject POSTs whose `Origin` or `Referer` is not the application's own origin.
3. Set `SameSite=Lax` (or `Strict` for logout and admin endpoints) on the PHPSESSID cookie as additional mitigation.
4. For the API router (`/api/v1/*`) continue requiring a bearer token in `Authorization` (not an ambient cookie) — this is already architecturally safer; just fix the Apache header-stripping configuration separately (see informational finding).

# Finding: Publicly reachable PostgreSQL database on port 5432
Severity: high
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H
Affected: 51.161.131.44:5432/tcp (OVH Sydney VPS, hosting imagesharer.xyz)
References:
- CWE-668 Exposure of Resource to Wrong Sphere
- CIS Benchmark PostgreSQL: do not expose 5432 to the internet

Summary:
The PostgreSQL instance that backs the application is reachable from the public internet on `51.161.131.44:5432`. The service responds to the standard protocol handshake. Although credentials were not attempted during the engagement (per scope), the exposure itself is a serious finding: it allows any Internet attacker to attempt authentication, exploit any CVE in the DB server, and probe the service continuously; it also removes a critical defense boundary.

Description:
Confirmation via a safe `nmap -sV` probe:

    PORT     STATE SERVICE    VERSION
    5432/tcp open  postgresql PostgreSQL DB
    server supports 3.0 to 3.0  (postmaster.c:2222)

The server returned a `FATAL` message from `postmaster.c:2222` to an invalid protocol version probe, confirming the service is listening and reachable without a TLS handshake requirement. No authentication was attempted and no SQL was executed per engagement scope.

Business impact:
- Any attacker can continuously attempt credential-based access, exploit DB CVEs, or disrupt the service.
- Should a credential ever leak (as the AWS key did), the database is one network hop away.
- Removes network isolation that is universally expected to protect a DB tier.

1. Firewall port 5432 so it is only reachable from the application host(s) that need it. On OVH this can be done at the host firewall (ufw / nftables / iptables) and in the OVH control panel.

# Finding: Open recursive DNS resolver on port 53
Severity: medium
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:N/I:N/A:L
Affected: 51.161.131.44:53/tcp (and almost certainly 53/udp)
References:
- CWE-406 Insufficient Control of Network Message Volume (Network Amplification)
- US-CERT TA14-017A — DNS amplification attacks
- CIS Controls — do not expose recursive DNS to the Internet

Summary:
The VPS answers recursive DNS queries for arbitrary external names from any source IP on the Internet. This both exposes the host to being abused as an amplification reflector in DDoS attacks against third parties and leaks hints about internal infrastructure/queries.

Description:
`dig +tcp @51.161.131.44 example.com a +rec` returned a standard answer with the `ra` (recursion available) flag set. `+norec` queries were also answered. Standard CHAOS probes (`version.bind`, `hostname.bind`) returned NXDOMAIN (good — software version not disclosed). AXFR for `imagesharer.xyz` was correctly refused.

The server appears to be a locally-running resolver (likely `systemd-resolved`, `bind9`, or `unbound`) that is unintentionally bound to the public interface rather than loopback.

Business impact:
- The VPS can be weaponized to amplify UDP-based DDoS traffic at other victims, which can get the IP (and by extension the hosting account) null-routed or rate-limited by OVH.
- Potential privacy leak if any internal names are inadvertently resolved.
- Reputation and abuse-complaint risk.

Recommendation:
1. Bind the resolver to `127.0.0.1` only (e.g., `listen-on { 127.0.0.1; };` in bind9 or `DNSStubListener=no` + `[Resolve] DNSStubListener=no` in `systemd-resolved`).
2. Alternatively, firewall `53/tcp` and `53/udp` so the outside world cannot reach it; the application does not need to receive DNS from the Internet.
3. If a public authoritative DNS is a real requirement, split authoritative from recursive and set `recursion no;` on the authoritative instance.

Severity: medium
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:L/A:L
Affected: http://51.161.131.44:8080/ (Apache/2.4.68 + PHP 8.2.34)
References:
- CWE-693 Protection Mechanism Failure
- OWASP ASVS V13 — API security

Summary:
The Apache HTTP server on port 8080 serves the same Imager application that nginx reverse-proxies on 443/TCP. Any protective behavior added by nginx (TLS termination, rate limits, WAF rules, custom error pages, access logs, header rewrites) is trivially bypassed by connecting to the backend host directly.

Description:
`GET http://51.161.131.44:8080/` returned `HTTP/1.1 302 Found`, redirecting to `/dashboard`, with `Server: Apache/2.4.68 (Debian)` and `X-Powered-By: PHP/8.2.34` — the same application state as the nginx-fronted stack. - WAF / rate-limiting / IP allow-listing applied at the nginx layer can be trivially bypassed.

3. Harden Apache's default pages so backend software and port details are not disclosed on errors (`ServerTokens Prod`, `ServerSignature Off`).

# Finding: Verbose error messages leak source file paths and database schema (information disclosure)
Severity: medium
CVSS: CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:L/I:N/A:N
Affected:
- POST https://imagesharer.xyz/images/upload (triggers on bad `user_id` input)
References:
- CWE-209 Generation of Error Message Containing Sensitive Information
- OWASP A05:2021 Security Misconfiguration

Summary:
When the image upload controller receives an invalid or missing `user_id` field, the server responds with HTTP 500 and a JSON body that includes the full server-side file path, line number, and (for DB errors) the underlying PostgreSQL error with parameterized query details.

Description:
Observed responses:

- Blank `user_id` field →
  `{"error":{"code":"INTERNAL_ERROR","message":"An unexpected error occurred.","detail":"SQLSTATE[22P02]: Invalid text representation: 7 ERROR:  invalid input syntax for type uuid: \"\"\nCONTEXT:  unnamed portal parameter $2 = '' in /var/www/html/src/modules/images/ImagesService.php:71"}}`
- Missing `user_id` field →
  `{"error":{"code":"INTERNAL_ERROR","message":"An unexpected error occurred.","detail":"Undefined array key \"user_id\" in /var/www/html/src/UI/ImagesUiController.php:42"}}`

These responses disclose:
- Document root (`/var/www/html/`)
- Internal module structure (`src/modules/images/`, `src/UI/`)
- Specific class/file names (`ImagesService.php`, `ImagesUiController.php`)
- PostgreSQL as the backend database
- Parameterized query index (`$2`) — on the positive side, this also confirms prepared statements are in use (reducing SQL injection risk via that parameter)

- Dramatically shortens an attacker's reconnaissance phase.

3. Validate inputs (`user_id` must be a UUID; missing fields should fail validation long before touching the DB) and return `400 Bad Request` with a safe message instead of letting exceptions bubble up.

# Finding: PHPSESSID session cookie missing Secure, HttpOnly, and SameSite flags
Severity: medium
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:U/C:H/I:L/A:N
Affected: Set-Cookie: PHPSESSID on https://imagesharer.xyz/
References:
- CWE-614 Sensitive Cookie Without 'Secure' Attribute
- CWE-1004 Sensitive Cookie Without 'HttpOnly' Flag
- OWASP ASVS V3.4

Summary:
The PHP session cookie that authenticates every logged-in user is set without `Secure`, `HttpOnly`, or `SameSite` attributes. Consequently any cross-site scripting flaw becomes a session takeover, any downgrade to HTTP leaks the session, and the browser's `SameSite=Lax` default protections do not apply.

Description:
Captured header after login:

    Set-Cookie: PHPSESSID=2ed7842369a4730ec17ac3e55dfe623e; path=/

For contrast, the application does set security attributes on other cookies in the same response:

    Set-Cookie: last_login=...; secure; HttpOnly; SameSite=Lax
    Set-Cookie: page_views=...; secure; HttpOnly; SameSite=Lax

So the application is clearly aware of the flags; the PHPSESSID emission just does not include them, which strongly suggests the default `session_set_cookie_params` call is missing or incomplete.

A related issue: the `last_login` cookie body contains the raw session identifier (JSON `{"session_id":"<the-PHPSESSID>",...}`), persisted for 30 days. Even though it is marked `HttpOnly`, this cookie is a secondary place where the session ID can be exposed (e.g., in server-side log reflections, XSS that reads cookies by name, or over any non-HTTPS leg of the request). The session identifier should never be stored anywhere other than the `PHPSESSID` cookie itself.

Business impact:
- A single reflected or stored XSS anywhere in the application yields full account takeover.
- Any accidental HTTP endpoint (e.g., a redirect misconfiguration) leaks sessions on the network.
- CSRF is harder to mitigate because the browser's SameSite default is not engaged.

Recommendation:
1. Set the session cookie to `Secure; HttpOnly; SameSite=Lax` (or `Strict` for admin flows). In PHP:
   `session_set_cookie_params(['lifetime' => 0, 'path' => '/', 'secure' => true, 'httponly' => true, 'samesite' => 'Lax']);`
2. Stop including the session identifier in the `last_login` cookie — a timestamp is enough; drop `session_id` from that payload.
3. Rotate the session ID (`session_regenerate_id(true)`) on each privilege change (login already does this; make sure logout + password-change also do).

# Finding: Open user enumeration via /register endpoint
Severity: medium
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N
Affected: POST https://imagesharer.xyz/register
References:
- CWE-204 Observable Response Discrepancy
- OWASP ASVS V3.1 — Session Management

Summary:
POSTing a candidate email to `/register` returns a 302 with `Location: /register` if the email already exists on the service, and `Location: /dashboard` if it does not (because the new account is created and auto-logged-in). An attacker can enumerate the entire user base by submitting candidate emails and observing the redirect target.

Description:
- Existing email `clawsec.a.1791171194@mailinator.com` → `302 ... Location: /register`

- Privacy exposure (service membership can be learned without the user's consent).

2. Add a verification email requirement for new accounts so that creating an account cannot be used as a side-channel at all.
3. Add rate limiting (next finding) so even response-timing differences cannot be exploited at scale.

# Finding: No rate limiting on /login, /register, or /api/v1/auth/login
Severity: medium
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:L/A:L
Affected: /login, /register, /api/v1/auth/login
References:
- CWE-307 Improper Restriction of Excessive Authentication Attempts
- CWE-770 Allocation of Resources Without Limits or Throttling
- OWASP ASVS V2.2

Summary:
Login, registration, and API login endpoints accept successive requests from the same source without any rate limiting, delay, lockout, or CAPTCHA. (Observed: 10 bad-password login attempts in ~5 seconds all answered normally; 5 register attempts with unique emails all accepted.) This is a necessary precondition for password spraying, credential stuffing, bulk user enumeration, and spam-account creation. The engagement scope prohibited actually brute-forcing credentials; the lack of protection is itself the finding.

Business impact:
- Credentials with weak passwords (minimum 8 chars, no complexity requirement observed) are at high risk of being guessed.
- Mass account creation is possible (automated spam, resource consumption, S3 object proliferation).
- User enumeration (previous finding) scales trivially without this control.

Recommendation:
1. Implement per-IP and per-account rate limits on `/login`, `/register`, `/api/v1/auth/login`, `/profile/avatar`, and `/images/upload`. A sensible starting point is 5 attempts / minute / account for auth endpoints, with exponential backoff; and 10 uploads / minute / user for upload endpoints.
2. Add account lockout + alert on repeated failed logins against the same username.
3. Add a modern CAPTCHA (e.g., hCaptcha / Turnstile) to registration and password-forgot flows (the latter does not currently exist — see separate finding).
4. Monitor and alert on unusual patterns (many failed logins to different accounts from one IP = credential stuffing).

The image upload endpoint accepts files whose filenames end in `.jpg.php` and whose body contains JPEG magic bytes followed by PHP source code. The avatar upload endpoint rejects the same files, indicating the two upload paths use different validators and the images path is weaker. The uploads are stored on S3 and re-keyed to `<uuid>.jpg`, which stops direct code execution — but hostile content still enters user storage, and the server-side renaming is the only thing between a bad upload and a persistent exploit.

Description:
Test matrix (`/images/upload`, authenticated as account A, with the correct `user_id`):

| Filename sent | Content-Type | Content | Result |
|---|---|---|---|
| xss.svg | image/svg+xml | SVG with `<script>` | 302 → /images/upload (rejected) |
| shell.php | application/x-php | `<?php phpinfo(); ?>` | 302 → /images/upload (rejected) |
| shell.jpg.php | image/jpeg | pure PHP | 302 → /images/upload (rejected) |
| magic_php.jpg | image/jpeg | JPEG header + `<?php ... ?>` | 302 → /images/<new-id> (ACCEPTED) |
| double_ext.jpg.php | image/jpeg | JPEG header + `<?php ... ?>` | 302 → /images/<new-id> (ACCEPTED) |

The accepted files were renamed to `<image-uuid>.jpg` on S3, which prevents direct `.php` execution. But the application endpoint `/images/<uuid>` still serves these to users as the application's "image," meaning hostile content now lives under a victim's account (chainable with the BOLA finding) and will be served to any viewer with a believable preview thumbnail.

The avatar endpoint rejected all of the same test files, proving the application has a stronger validator — it just is not applied uniformly.

Business impact:
- The weaker image-upload path accepts polyglots that can carry secondary payloads (abusive content hidden in images, data exfiltration via image steganography, EXIF-stored payloads).
- Combined with BOLA and CSRF, an attacker can plant hostile files under a victim's account without the victim's awareness.
- Any future change that treats uploaded files by filename (image resizers, antivirus scanners, OCR, download endpoints) is at risk.

Recommendation:
1. Reuse the exact validator used by `/profile/avatar` on `/images/upload`.
2. Validate uploads server-side by (a) MIME type sniffing of the first N bytes (`finfo_file`), (b) image parsing via GD/Imagick to confirm it is a valid image of the expected type, and (c) strict allow-list of extensions.
3. Always re-encode uploaded images (decode → re-encode as JPEG/PNG/WebP) to strip EXIF/embedded payloads/polyglot tails. This also prevents EXIF-based data exfiltration and some stored-XSS techniques.
4. Enforce the type on the S3 object metadata (`Content-Type: image/*`, `Content-Disposition: inline`, consider `X-Content-Type-Options: nosniff` at the CDN layer).

# Finding: Missing security headers (HSTS, Content-Security-Policy, Permissions-Policy)
Severity: low
CVSS: CVSS:3.1/AV:N/AC:H/PR:N/UI:R/S:U/C:L/I:L/A:N
Affected: all responses from https://imagesharer.xyz/
References:
- OWASP Secure Headers Project
- MDN Web Security

Summary:
The web application returns some good headers (X-Frame-Options, X-Content-Type-Options, Referrer-Policy, X-XSS-Protection) but omits HSTS, Content-Security-Policy, and Permissions-Policy. HSTS absence allows a first-visit downgrade to HTTP, CSP absence removes a critical mitigation against XSS, and Permissions-Policy absence lets any embedded resource request camera, microphone, geolocation, etc.

Description:
Observed response headers (consistent across the site):

    X-Content-Type-Options: nosniff
    X-Frame-Options: DENY
    X-XSS-Protection: 1; mode=block
    Referrer-Policy: strict-origin-when-cross-origin

Missing:
- `Strict-Transport-Security`
- `Content-Security-Policy`
- `Permissions-Policy`
- `Cross-Origin-Opener-Policy` / `Cross-Origin-Embedder-Policy` / `Cross-Origin-Resource-Policy` (defense-in-depth)

Business impact:
- A user who types `imagesharer.xyz` into their browser bar lands on HTTP first; without HSTS, a network attacker can keep them on HTTP.
- Any XSS vulnerability (none proven exploitable here, but the attack surface is large) could be dramatically mitigated by a tight CSP.
- Future features that embed third-party content inherit the (lack of) policy.

Recommendation:
1. Add on all HTML responses:
   - `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload` (consider submitting the domain to the HSTS preload list after a short observation window).
   - `Content-Security-Policy: default-src 'self'; img-src 'self' https://*.s3.ap-southeast-2.amazonaws.com data:; script-src 'self'; style-src 'self' 'unsafe-inline'; object-src 'none'; frame-ancestors 'none'; base-uri 'self'; form-action 'self';` (tune to the real asset set).
   - `Permissions-Policy: geolocation=(), microphone=(), camera=(), payment=()` (deny everything the app doesn't need).
2. Add a CAA record on the apex domain restricting issuance to the current CA (Let's Encrypt): `imagesharer.xyz. CAA 0 issue "letsencrypt.org"`.
3. Drop the deprecated `X-XSS-Protection` header (it is removed from modern browsers) and replace with a CSP.

# Finding: Email domain lacks SPF, DMARC, DKIM, and MX records — email spoofing permitted
Severity: low
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:C/C:N/I:L/A:N
Affected: imagesharer.xyz (DNS zone)
References:
- CWE-290 Authentication Bypass by Spoofing
- RFC 7489 (DMARC)

Summary:
`imagesharer.xyz` has no MX, SPF, DMARC, or DKIM records. Any attacker can send email appearing to come from `@imagesharer.xyz` to users or partners, with no reliable way for the receiving mail server to detect the forgery. This is especially risky if the service ever sends email (password reset, security notifications), because recipients cannot distinguish real messages from spoofed ones.

Description:
Direct DNS queries returned nothing:

    MX imagesharer.xyz          -> no answer
    TXT imagesharer.xyz         -> no SPF record
    TXT _dmarc.imagesharer.xyz  -> no DMARC record
    TXT default._domainkey.imagesharer.xyz -> no DKIM record

Business impact:
- Phishing from `@imagesharer.xyz` cannot be filtered confidently by downstream mail systems.
- If the service plans to send email, any legitimate mail may land in spam.
- Reputational and legal risk if users are deceived.

Recommendation:
1. Publish a hard-fail SPF record even if the domain never sends mail:
   `imagesharer.xyz. TXT "v=spf1 -all"`
2. Publish a reject-policy DMARC record:
   `_dmarc.imagesharer.xyz. TXT "v=DMARC1; p=reject; sp=reject; rua=mailto:dmarc@imagesharer.xyz"`
3. When outbound mail is introduced, add the corresponding sending-service SPF include and a DKIM TXT at a selector managed by the sender; keep DMARC at `p=reject`.
4. Even without inbound mail, publish an MX that returns `"."` (null MX, RFC 7505) to signal that the domain does not receive mail:
   `imagesharer.xyz. MX 0 "."`

# Finding: 7-day pre-signed URLs for public images are excessive given the bucket is public anyway
Severity: low

# Finding: Password policy weak and no password-change / password-reset flow exists
Severity: low
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:U/C:L/I:L/A:N
Affected:
- POST https://imagesharer.xyz/register (sets passwords with no complexity requirement)

References:
- OWASP ASVS V2.1 — Password Security
- NIST SP 800-63B

Summary:
Registration accepts passwords of 8+ characters with no complexity, dictionary, breached-password, or entropy checks. There is no way for a logged-in user to change their password, and no public password-reset / forgot-password route exists. # Finding: Backend trusts client-supplied `user_id` parameter and bubbles unvalidated input into database queries and storage paths
Severity: medium
CVSS: CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:C/C:L/I:L/A:N
Affected: POST https://imagesharer.xyz/images/upload (and almost certainly related endpoints)
References:
- CWE-20 Improper Input Validation
- CWE-915 Improperly Controlled Modification of Dynamically-Determined Object Attributes (mass assignment)

Summary:
The upload handler forwards the client-supplied `user_id` form field directly into the SQL layer and into the S3 object key. Along with the ownership bypass already documented (BOLA finding), this permits attacker control over the storage prefix of the object, which has produced persistent artifacts in the bucket (e.g., the key `users/'/a5cebccb-...png` demonstrates `user_id='` reaching the storage path).

Description:
Observed effects when tampering with the `user_id` form field:
- Valid UUID of another user → file stored under that user's prefix (see BOLA finding)
- `../../etc` → request rejected to `/images/upload` (filter catches `..`)
- `' or 1=1 --` → HTTP 500 with the PostgreSQL error `invalid input syntax for type uuid` (the DB prepared statement rejects the type-coerce, which incidentally prevents SQLi via this parameter)
- blank or missing → HTTP 500 with PHP source paths (information disclosure finding)
- The public bucket contains `users/'/...` showing that at least once in the past, a single apostrophe survived the controller and made it onto the storage path

Business impact:
- Attackers can seed garbage keys into the bucket (`users/<attacker-chosen-prefix>/<uuid>.jpg`), causing operational mess and complicating any later "delete all my data" request.
- Even where PostgreSQL's strict UUID type rejects malformed values, the application should not depend on database type-coercion as its input validator.
- Any future query that doesn't go through the UUID-typed parameter (e.g., a free-text `WHERE email = ?` elsewhere) carries the same trust problem.

Recommendation:
1. Validate every `user_id` field against the UUID format in the UI controller (`ImagesUiController.php`) BEFORE any DB or storage access. Reject with 400 on failure.
2. More importantly: do not read `user_id` from the request at all — read it from the authenticated session (see BOLA finding). This removes the whole category.
3. Delete any existing bucket keys whose prefix is not a well-formed UUID (`users/'/`, `users/00000000-0000-0000-0000-000000000000/`, etc.) — they are leftover from earlier probing and have no legitimate owner.
4. Apply the same lesson to all other controllers: trust nothing from the client that duplicates server-known state.

# Finding: API authentication is functionally unreachable because the Authorization header is stripped before PHP (configuration bug)
Severity: info
CVSS: n/a
Affected: /api/v1/* on both nginx (443) and Apache (8080)
References:
- Apache docs — `CGIPassAuth`, `SetEnvIf Authorization`
- PHP docs — $_SERVER['HTTP_AUTHORIZATION']

Summary:
The REST API accepts a POST to `/api/v1/auth/login`, returns a JWT, and advertises a Bearer-token flow. In practice no authenticated API request succeeds, because `Authorization: Bearer <token>` is stripped by the server stack before PHP sees it; the API always answers `401 UNAUTHORIZED — Authentication token is required`. This is a configuration/functionality bug rather than an attacker-exploitable vulnerability, but it means the whole `/api/v1/*` surface is dead and any security claims about it are unverifiable.

Description:
- `POST /api/v1/auth/login` with valid credentials returns an HS256 JWT (payload: `{"iss":"imager","sub":"<user-uuid>","iat":<ts>,"exp":<ts+86400>}`), 24-hour lifetime.
- Replaying that token in `Authorization: Bearer`, `authorization: bearer`, `X-Auth-Token`, `?token=`, `Proxy-Authorization`, and `Cookie: token=` all yield the same 401 "Authentication token is required."
- This behavior is observed BOTH on the nginx-fronted 443 and on the direct Apache 8080 — so this is PHP configuration (`CGIPassAuth off`-like default) rather than nginx.

Business impact:
- The API is effectively non-functional for any client that uses it, which has no security consequence by itself but points to an untested code path. Once fixed, the API would need to be re-audited (JWT secret strength, revocation, scopes, etc.).

Recommendation:
1. In Apache, add `SetEnvIf Authorization "(.*)" HTTP_AUTHORIZATION=$1` (or `CGIPassAuth On` in a `<Directory>` block) so the `Authorization` header reaches PHP.
2. In nginx with FastCGI, add `fastcgi_pass_header Authorization;`.
3. After fixing, verify the JWT verification path:
   - Confirm `alg: none` is rejected.
   - Confirm the HS256 secret is high entropy (≥ 256 bits of randomness, not a dictionary word) — the current secret could not be brute-forced in this engagement (not permitted) but should be reviewed.
   - Confirm the API also derives authorization from the JWT `sub` and never from a client-supplied `user_id` field (see BOLA finding) — any re-enabled API endpoint should pass the same ownership tests.
