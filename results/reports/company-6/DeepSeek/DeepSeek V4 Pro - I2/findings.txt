# Finding: Default administrator credentials on admin login
Severity: critical
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H
Affected: https://ausecurity.best/ (API /api/auth/login, admin panel)
References: https://cwe.mitre.org/data/definitions/798.html

Summary:
The administrative login of the AuSecurity web application accepts well-known default
credentials (admin / admin). Anyone who can reach the site can sign in as administrator.

Description:
A POST to /api/auth/login with {"username":"admin","password":"admin"} returns HTTP 200
and {"success":true}, and issues a signed "admin_token" session cookie (HttpOnly, Max-Age
3600). The login endpoint is also reachable over plain HTTP on port 8080. This grants an
unauthenticated attacker full administrative access to the management interface, from
which they could view and manipulate client data and the application.

Recommendation:
Immediately rotate the administrator password to a strong unique value, enforce account
lockout/rate limiting on the login endpoint, disable the plain-HTTP port (8080), and
require multi-factor authentication for administrative accounts.

# Finding: Admin dashboard accessible without authentication (client data exposure)
Severity: high
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N
Affected: https://ausecurity.best/dashboard.html and /dashboard (also 51.79.166.148:8080)
References: https://cwe.mitre.org/data/definitions/306.html

Summary:
The administrator dashboard is served to unauthenticated visitors and exposes business
metrics, revenue figures, and personally identifiable information of clients.

Description:
GET /dashboard (and /dashboard.html) returns HTTP 200 without any authentication
challenge. The page hard-codes: aggregate counters (enquiries, active clients,
assessments, proposals), a "Recent Enquiries" panel listing ~5 client enquiries with
company names, contact-person names, and email addresses, an activity log referencing
client engagements, and a year-to-date revenue figure. The same page is served unencrypted
over HTTP on port 8080. This is a broken-access-control issue combined with sensitive
information disclosure (client PII and business intelligence).

Recommendation:
Enforce server-side authentication and authorization on the dashboard (and its backing
data) rather than relying on client-side checks. Remove business/PII data from static
HTML and load it via authenticated API calls only. Disable the plain-HTTP service on 8080.

# Finding: osTicket installation wizard exposed to unauthenticated users
Severity: critical
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H
Affected: https://ticket.ausecurity.best/ (51.79.166.209)
References: https://docs.osticket.com/en/latest/Getting%20Started/Installation.html

Summary:
The osTicket helpdesk (v1.18.4) has not been configured and exposes its full installation
wizard to anonymous users, including the database-configuration step.

Description:
The root path and the staff control panel (/scp/login.php) both redirect (302) to
/setup/install.php. The installer ("osTicket v1.18.4") is reachable unauthenticated and
walks through prerequisite and database configuration. A remote attacker can complete the
installation themselves (binding the application to a database they control or to the
internal database if reachable), effectively taking over the ticketing system. The
deployment has been left in its pre-installation state.

Recommendation:
Complete or remove the installation immediately and delete the /setup/ directory from the
web root. Place the helpdesk behind the intended access controls before exposing it, and
confirm the staff control panel is only reachable after configuration.

# Finding: DOM-based cross-site scripting via "name" parameter (success page)
Severity: medium
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:C/C:L/I:L/A:N
Affected: https://ausecurity.best/consultation-success.html
References: https://cwe.mitre.org/data/definitions/79.html

Summary:
The consultation-success page reflects the "name" URL parameter into the DOM using
innerHTML without sanitization, allowing arbitrary script execution in the victim's browser.

Description:
An inline script reads the "name" query parameter and assigns it to the #user-name element
via innerHTML (a classic DOM XSS sink). A crafted URL such as
/consultation-success.html?name=<img src=x onerror=...> executes attacker-controlled
JavaScript in the page context. This was verified by loading a payload that changed the
document title. The /api/contact endpoint further reflects the submitted full_name value
into a redirect_url that points at this page, creating a self-XSS-to-URL chain.

Recommendation:
Use textContent (or an equivalent safe API) instead of innerHTML for untrusted values, and
URL-encode/sanitize reflected values. Apply a Content-Security-Policy that restricts script
sources.

# Finding: Missing security response headers
Severity: medium
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:U/C:L/I:L/A:N
Affected: https://ausecurity.best/ (all public pages)
References: https://owasp.org/www-project-secure-headers/

Summary:
The main website omits several important security headers, weakening protection against
clickjacking, MIME sniffing, and connection downgrade.

Description:
Public pages (index, services, about, case-studies, contact, login, dashboard) are served
without Strict-Transport-Security (HSTS), Content-Security-Policy (CSP),
X-Content-Type-Options, and (on most pages) X-Frame-Options and Referrer-Policy. The login
and dashboard pages set X-Frame-Options: DENY, but the marketing pages do not, and no HSTS
is sent anywhere, allowing HTTP-based downgrade and MITM.

Recommendation:
Add a consistent set of security headers, including Strict-Transport-Security,
Content-Security-Policy, X-Content-Type-Options: nosniff, X-Frame-Options (or CSP
frame-ancestors), and Referrer-Policy, and enforce HTTPS site-wide with an HTTP-to-HTTPS
redirect.

# Finding: Self-signed TLS certificate on main site
Severity: medium
CVSS: CVSS:3.1/AV:N/AC:H/PR:N/UI:R/S:U/C:L/I:L/A:N
Affected: https://ausecurity.best/
References: https://cwe.mitre.org/data/definitions/295.html

Summary:
The main website presents a self-signed TLS certificate that cannot be validated against a
trusted CA, exposing visitors to man-in-the-middle risk and browser trust warnings.

Description:
The certificate for ausecurity.best is self-signed (issuer == subject), has no certificate
transparency log entry, and fails OpenSSL verification (error 18, self-signed). The blog
and ticket hosts use their own certificates. Visitors must bypass browser warnings to use
the site, and traffic cannot be verified as authentic.

Recommendation:
Deploy a certificate from a trusted public CA (e.g., Let's Encrypt) and enable automatic
renewal. Consider a wildcard/SAN certificate covering all subdomains.

# Finding: Admin panel and full site served over plain HTTP on port 8080
Severity: medium
CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:L/A:N
Affected: 51.79.166.148:8080 (ausecurity.best)
References: https://cwe.mitre.org/data/definitions/319.html

Summary:
The same web application (including the admin dashboard and login) is served unencrypted
over HTTP on port 8080.

Description:
Port 8080 on 51.79.166.148 serves nginx/1.25.5 returning the identical site content over
plain HTTP with no TLS. This includes the login page and the admin dashboard. Credentials
and session cookies transmitted via this port are exposed to network eavesdropping.

Recommendation:
Close port 8080 externally or redirect it to HTTPS. Serve the application exclusively over
TLS.

References: https://cwe.mitre.org/data/definitions/200.html

Summary:
The WordPress blog discloses the "admin" username through the author-archive redirect.

Description:
Requesting /?author=1 returns a 301 redirect (X-Redirect-By: WordPress) to

# Finding: Contact API returns unhandled server error for unexpected routing field
Severity: info
CVSS:
Affected: https://ausecurity.best/api/contact
References: https://cwe.mitre.org/data/definitions/20.html

Summary:
Submitting an unexpected value in the "h" routing field causes an unhandled HTTP 500 error.

Description:
The contact endpoint accepts a client-supplied "h" field. Sending an unexpected value
(e.g., "evil.example.com") returns HTTP 500 "Internal Server Error" with a generic body,
indicating insufficient input validation and error handling (and confirming the field is
processed server-side). No stack trace was leaked.

Recommendation:
Validate and restrict the "h" field to an allowlist of known hostnames and return a
structured 4xx response for invalid values.

# Finding: Technology and version information disclosure
Severity: info
CVSS:
Affected: ausecurity.best, blog.ausecurity.best, ticket.ausecurity.best
References: https://cwe.mitre.org/data/definitions/200.html

Summary:
Multiple components disclose their exact software versions and framework fingerprints.

Description:
Observed disclosures include nginx/1.22.1 and nginx/1.25.5 (also visible in the 404 page
footer, indicating a reverse proxy), PHP/8.2.33 (X-Powered-By on ticket), Apache/2.4.68
(Debian), osTicket v1.18.4, WordPress version, and FastAPI/Starlette-style JSON error
envelopes on the API. These fingerprints help attackers select known exploits.

Recommendation:
Suppress version banners (server_tokens off, expose_php off, remove X-Powered-By), and
return generic error responses for the API.
